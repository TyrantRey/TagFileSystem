# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

TagFileSystem is a per-root daemon: it watches a managed folder, keys every file in SQLite, parses tags and add-on functions out of names (`@@make_copy__.jpg__backup/2024--trip/img--raw.jpg`), runs user-written add-ons from `script/` on the files that ask for them, and records runs, traces, provenance and problems so a human, the `tfs` CLI or later an MCP client can query them. Python 3.12, managed with `uv` (src layout, `uv_build` backend). Every source file starts with `# Code by AkinoAlice@TyrantRey` except empty file.

`DESIGN/` holds the approved designs, one file per release, named `v{A}-{B}-{C}.md` after the version it specifies: `DESIGN/v0-1-0.md` is the v1 design (2026-08-30, shipped in 0.1.0), `DESIGN/v0-2-0.md` is the self-update design (approved and implemented 2026-09-02, shipped in 0.2.0; its closing "Implementation notes" list where the code deliberately differs), `DESIGN/v0-3-0.md` is the daemon lifecycle hooks `on_start`/`on_stop` (approved and implemented 2026-09-02, shipped in 0.3.0). A design wins over this file for **target** behaviour; this file describes the code **as it is**. Source docstrings cite them in full (`DESIGN/v0-1-0.md §7`); an unqualified `DESIGN §N` below means `DESIGN/v0-1-0.md`. Read the relevant design before changing the name grammar, schema, configuration, CLI or run semantics; update both when behaviour changes. `README.md` is the user-facing short version.

## Commands

```bash
uv sync                                   # install deps + editable install (registers the `tfs` script)
uv run tfs init <dir>                     # create a root: <dir>/.tfs/{config.toml, db/, token} + <dir>/script/
uv run tfs start [-d] [--force]           # reconcile + watch (foreground; -d detaches, output in .tfs/daemon.out)
uv run tfs list | query -t x --json | reload | stop
uv run tfs --version                      # "0.3.0 (abc1234)": pyproject version + git HEAD of the checkout
uv run tfs update [--json]                # fetch origin's release tags and report; changes nothing
uv run tfs upgrade [--to TAG] [--dry-run] [--yes] [--skip-tests] [--wait SEC]   # DESIGN/v0-2-0.md §7
uv run tfs backup list | prune --keep 3   # the snapshots in .tfs/backups/
uv run ty check src tests                 # type check (must be clean; CI also runs --python-platform linux)
uv run ruff format src tests              # format (CI checks it); run before every commit
uv run pytest -q                          # tests (~2 min; every test builds its own temporary root)
```

- Every command takes `--root <dir>`; otherwise the root is discovered by walking up from CWD like git. Every root-scoped command also records its root in the registry (`TFS_REGISTRY` overrides the location).
- Linting/formatting is configured for Trunk (`.trunk/trunk.yaml`: ruff `B,D3,E,F` with `E501` ignored, black, isort profile=black, bandit, markdownlint, prettier). The `trunk` CLI is not installed on this machine.
- Tests: `tests/helpers.py` has `fetch` / `metadata_of` / `tag_of` (assert-narrow `Optional` results so `ty check tests` stays clean). Tests that load add-ons carry a `clean_modules` fixture that drops `tfs_addons.*` from `sys.modules`. Daemon/CLI tests pick a free port and write it into the root's `config.toml`. `conftest.py` points `TFS_REGISTRY` at a per-test file (autouse). `tests/fakerepo.py` builds a git checkout shaped like this project with two release tags and a bare `origin`; `tests/fake_tools.py` stands in for `uv`, `pytest` and `tfs` (its fake daemon writes a real lock and answers `/health` and `/stop`) so `tests/test_upgrade.py` runs the real orchestrator end to end.

## Versioning

`version` in `pyproject.toml` is `A.B.C`: **A** = major update (breaks an existing root, the name grammar or the CLI), **B** = feature added (backwards compatible), **C** = changes update (fix, refactor, typo). A typo is a small change, so it is a C: `+0.0.1`. Bumping A resets B and C to `0`; bumping B resets C. Bump it in the same commit as the change it describes, and keep `README.md`'s Versioning section in step. Design documents carry the same numbers: `DESIGN/v{A}-{B}-{C}.md`.

## Architecture (by layer, bottom up)

**Paths and root (`core/paths.py`, `root.py`)** — DESIGN §2. `is_anchored` / `posix_key` / `has_parent_reference` answer path questions for *either* OS flavour. `Root.init(dir)` creates the layout (refuses if the dir, an ancestor or a descendant already has `.tfs/`, or if a file is in the way; cleans up on failure); `Root.discover(start)` walks up (`NotARoot`). `Root.relative(path)` **resolves** the path (symlinks, `..`, 8.3 names, case) and returns a `PurePosixPath` key or raises `OutsideRoot`; `absolute(key)` rejects anchored keys, `..`, and drive-relative `D:x` on Windows; `zone(path)` → `Zone.TFS` (any `.tfs` component, `os.path.normcase`) / `SCRIPT` / `DATA`. `Lock(root).acquire(force=False, port=None, bind=None)` creates `.tfs/lock` **with content atomically** (temp file + `os.link`; `O_EXCL` fallback), judges staleness by pid on this host (`pid_alive`: never `os.kill` on Windows, access-denied = alive) and by age for other hosts, evicts stale locks by renaming them away, never evicts an unreadable lock younger than 2 s, and gives up after 5 s (`LockHeld` carries the holder's `LockInfo`). `force` takes over a foreign-host lock but raises `LockHeld` for a `LockInfo.is_live_local()` holder — one daemon per root, always. The daemon records the control address it opened (`bind` + `port`) in the lock, so every command reaches *that* daemon even when `config.toml` is edited or broken while it runs. `LockInfo.upgrade` marks the lock as a `tfs upgrade` marker (DESIGN/v0-2-0.md §7 step 3): its pid is the orchestrator's, so it is live/stale like any lock, `LockHeld` says "being upgraded", and `Daemon.startup()` reports a stale one as `lock.stale` mentioning the upgrade marker.

**Configuration (`config.py`)** — `Config` models `.tfs/config.toml`: `[logging] level/file`, `[daemon] bind/port/stop_timeout_seconds/run_warn_after_seconds`, `[remotes]`. `extra="forbid"`, strict numeric fields, `bind` must be an IP, `logging.file` root-relative without `..` or a drive, remotes are **verbatim strings** that must be absolute in either flavour. `loads/load` raise `ConfigError`; `dumps/write` use a small TOML writer. There is no `.env` any more.

**Name grammar (`services/tagging.py`, `core/interface/tag.py`)** — DESIGN §3. `TaggingParser.parse(segment)` parses one directory name or filename stem; `parse_path(root_relative_path, is_file=True)` parses every segment and merges parent-first (tags = union, first occurrence wins; actions = distinct `(name, args)` parent-first, filename last). Anchored paths and `..` are errors. `ActionCall` (frozen; `name` lowercased, `[a-z][a-z0-9_]*`, no leading/trailing `_`; `args` split on `__`, verbatim, NFC) and `Tag` (frozen, normalized) reject illegal characters (`: / \ < > | ? * "` and line breaks) and marker text. A bad marker becomes a `ParseProblem` and the rest still parses. `split_extension` drops the filename suffix unless it contains marker syntax.

**Persistence (`database/sqlite.py`, `database/migrations.py`, `database/action_store.py`, `core/interface/{database,file_metadata,action}.py`)** — DESIGN §7. `SQLiteBackend.init_database(path, root_dir)` opens one connection (`check_same_thread=False`, WAL, foreign keys) behind an `RLock` (`@transactional` writes, `@locked` reads; nested calls join the outer transaction) and runs `apply_migrations` (`PRAGMA user_version`; `SchemaTooNew`; `MigrationError` for a rootless open of a DB with absolute paths; migration 1 creates all tables, adds `files.mtime_ns`, rewrites `files.path` to root-relative POSIX, soft-deletes rows it cannot key and parks dead duplicates under `.tfs/duplicates/`; migration 2 — `SCHEMA_VERSION = 2`, DESIGN/v0-2-0.md §9 — adds the `upgrades` table and `action_runs.code_version/code_hash`). `SCHEMA_VERSION` must stay a one-line integer literal: `tfs upgrade` reads it out of the target tag with `git show` and a regex. **Paths are stored as root-relative POSIX keys** (`backend.key()`); `TaggedFile.path` is the key, `original_path` the host path. Files/tags semantics: `insert` revives a soft-deleted row in place, `delete` is soft, `modify` renames, `set_file_tags` makes the exact set, queries exclude deleted rows unless asked, `query_files(path_prefix=)` answers "under `@@f`". `ActionStore(backend)` shares the connection and lock: `register_action` (upsert by `(name, script_hash)`, monotonic `loaded_at`), `find_run`/`start_run` (key `(file_hash, action, hook, canonical args)`; `RunExists` unless `retry_of` names a final run with the same key; every run is stamped with `version.VERSION`/`COMMIT`), `finish_run` (terminal; `RunAlreadyFinal`), `mark_interrupted`, `add_trace`, provenance (`emitted` beats `observed`, repeated `observed` accumulates `ambiguous`), problems with `delivered_at`, `file_history` (+ `.timeline`), `query_runs(path_prefix=)`, `record_upgrade`/`query_upgrades` (`UpgradeRecord`; `tests_*` are `None` when the suite was skipped). `canonical_json` is the only JSON writer (sorted keys, explicit encoder, `TypeError` otherwise, no NaN).

**Add-on API (`action.py`, `addons/binding.py`, `addons/loader.py`)** — DESIGN §4.1–4.2, §4.4, DESIGN/v0-3-0.md §2. `from tag_file_system import action`: `@action.added() / .modified() / .removed(on_move=False) / .tagged("x") / .on_start() / .on_stop() / .crit() .err() .warn() .info()` mark a function (bare `@action.added` is a `TypeError`); `action.TagDir` / `action.Remote` annotate path-valued args. `binding`: parameters after `(path, metadata, ctx)` (2 for problem handlers, 1 — just `ctx` — for lifecycle handlers) are validated per parameter through cached `TypeAdapter`s; `raw_by_name` gives the run-key args (slug strings keyed by parameter name) even when binding fails; bare `Path`, `async def`, `*args`, positional-only and keyword-only fixed params are `SignatureError`s at load. Problem and lifecycle handlers bind nothing: a required parameter beyond the fixed ones is an `addon.signature` problem, since nothing could ever supply it. `AddonLoader.load_all()` execs every `script/*.py` from source into `tfs_addons.<name>` (no `__pycache__`); imports *from* a script (helpers `_x.py`, sibling add-ons) are served by `_ScriptFinder`, last in `sys.meta_path`, which resolves by the importing code's `__file__` to that root's `script/` (nothing on `sys.path`, installed modules are never shadowed, helpers shared within a root and reloaded on change, circular sibling imports resolve like packages). Rules: bad filenames → `addon.filename` (WARN), import failures incl. `SystemExit` → `addon.import` (previous version kept), bad signatures → `addon.signature`, a second handler per `(hook, tag)` → `addon.duplicate_handler` (lifecycle hooks included), no handlers of any kind → `addon.empty`, store failure → `db.unwritable`. `Addon.describe()` is the single source of what `tfs list` and `/actions` report; `AddonLoader.lifecycle_handlers(hook)` returns every add-on's `on_start`/`on_stop` handler, ordered by add-on name.

**Runner (`addons/runner.py`, `addons/context.py`)** — DESIGN §4.3, §4.5, §6, DESIGN/v0-3-0.md §4. `ActionRunner.on_file(hook, path, file, parsed, source, parent, moved)` / `on_tag(...)` run handlers parent-first: key first (`find_run` → skip), provenance guard (a file never re-triggers the action that produced it, for `added`/`modified`), then bind, and `_invoke` — the shared run body: `start_run`, call the handler with stdout/stderr/logging routed into its trace by a **thread-local dispatcher** installed once per process (streams and the root logger level are restored after each run), and finish `ok`/`failed`/`interrupted` with the matching problem. `on_lifecycle(hook)` goes through the same `_invoke` with `path`/`file` `None` and `call=handler.func`: `on_start`/`on_stop` runs are keyed `("", action, hook, {"session": runner.session})` — one uuid per `ActionRunner`, so the hook fires once per daemon session per add-on however often it is called, `source` is `lifecycle`, and `ctx.retry` refuses them (`retry.lifecycle` WARN). `ctx.copy/move/write/delete/emit` keep the DB in step (`Indexer`), record `emitted` provenance and chain the produced file's own tags and `@@` functions (`source=chain`, `parent_run_id`, depth ≤ 8). `ctx.spawn` makes the run thread-backed until `ctx.done()`; a dying thread fails the run; `check_overdue` raises `run.overdue` once (never for a lifecycle run: a service started in `on_start` is meant to outlive the threshold); `stop(timeout)` interrupts leftovers (P0). `problem()` records, then dispatches to `loader.problem_handlers` (level and above) with a thread-local recursion guard; problems raised by runs a handler starts are delivered after it returns. `retry` only for failed/interrupted runs whose file exists, at most `MAX_RETRIES` deep.

**Daemon (`services/daemon.py`, `services/indexer.py`, `services/control.py`, `core/logger.py`)** — DESIGN §5, §8. `Indexer.index(path)` is the one place a file becomes a row (stat; hash unless `(size, mtime_ns)` match; insert/update; tags = the name's tags plus whatever the previous row carried beyond *its* name). `Daemon(root, control=True)`: `startup()` = lock (`lock.stale`/`lock.overridden`), `mark_interrupted` leftovers (`run.interrupted` P0), control server, `load_all`, `on_lifecycle(ON_START)`, `replay_undelivered`, `reconcile()`; `run_forever()` feeds `watch(root)` batches to `process_changes()` and ticks `check_overdue`; `shutdown()` = `_stop_addons()` (`on_lifecycle(ON_STOP)`, so a handler can end the run its `on_start` left open), `runner.stop`, control stop, lock release, DB close. `_lifecycle_started` gates both: a daemon that never started runs no lifecycle hook, and every `_load` after startup (a script appearing, `tfs reload`) offers `on_start` to whatever is loaded — the run key makes that a no-op for the add-ons that already had their turn. `process_changes` consolidates (deleted > added > modified), routes by zone (`.tfs` ignored, `script/` → loader, data → files), detects **moves** (vanished row whose hash matches an added file → `backend.modify`, `removed(on_move=True)` for `@@` dirs left), reconciles added directories, fires `on_tag` for new tags then `on_file`, and attributes changes seen while runs are in flight as `observed` provenance (+ P2) — lifecycle runs excluded, since one is in flight for the whole session and would make every change ambiguous. `ControlServer` serves `/health` (with `version` and `hash`: the code this daemon runs), `/stop`, `/reload`, `/actions` (also `version`/`hash`), `/files` with `Authorization: Bearer <.tfs/token>`, bound **exclusively** (`SO_EXCLUSIVEADDRUSE`, `allow_reuse_address = False`) so two roots cannot share a port; `ControlClient` is what the CLI uses. `configure_logging` is called by `tfs start`, never at import.

**Version identity (`version.py`)** — DESIGN/v0-2-0.md §3. `VERSION` is read from the checkout's `pyproject.toml` first (the installed `.dist-info` goes stale on purpose after an upgrade, see below), then `importlib.metadata`; `COMMIT` is `HEAD` read straight out of `.git` (loose refs, `packed-refs`, worktree pointers; `git rev-parse` as fallback), `None` outside a checkout. Both are fixed at import so a daemon reports the code it actually runs. `describe()` is `0.2.0 (abc1234)`.

**Self-update (`updater.py`, `__main__.py`)** — DESIGN/v0-2-0.md. `updater.py` is **standard library only** (a test parses it and fails on any other import) because `tfs upgrade` copies it to a temporary directory and re-runs it there on the base interpreter (`sys._base_executable`) while `git checkout` and `uv sync` rewrite the checkout; it mirrors the lock format, root layout and control wire format it needs. Sections: the root registry (`registry_path()` = `%APPDATA%\tfs\roots.json` / `$XDG_CONFIG_HOME/tfs/roots.json`, `TFS_REGISTRY` overrides; `register_root` is best effort, `known_roots` prunes paths without `.tfs/`); git helpers (`remote_tags` = annotated tags from `git ls-remote --tags origin`, `head_state`, `file_at` = `git show`, `schema_version_in`/`project_version_in` regex+tomllib); `inspect_root` → `RootState` (running daemon from the lock, foreign-host lock → skipped, another marker → refused, `user_version` read-only); `write_marker`/`remove_marker`; `snapshot` (`VACUUM INTO` + `quick_check`), `list_backups`, `prune_backups`, `restore_snapshot` (drops `-wal`/`-shm`); `check()` (what `tfs update` reports, `Check.as_dict()`), `preflight()` → `Plan` (JSON round trip; `commands` overrides `uv`/`tfs`/`pytest` for tests; `_drain` waits `--wait` for in-flight runs, never interrupts one), `run_plan()` (steps 3–11: markers → stop via `/stop` and pid → snapshots → checkout `refs/tags/<tag>` + `uv sync --locked --no-install-project --inexact` → pytest → per running root remove marker, `python -P -m tag_file_system.cli start -d`, `/health` hash must equal the target commit → `record-upgrade` per root → retention → snapshot prompt; exit 0/1/2), `_revert` (stop new daemons, restore snapshots only when a daemon had started, checkout `from_ref`, sync, restart), `manual_steps`, `hand_off` (temp copy + `subprocess.run`), `main(argv)` (argparse; consent prompt only when the schema changes, `--yes` or a tty required). `__main__.main` is the `tfs` console script: it routes a bare `upgrade` subcommand to `updater.main` **before importing `cli`**, everything else to the Typer app.

**CLI (`cli.py`)** — DESIGN §8, DESIGN/v0-2-0.md §4. Typer app with `init`, `list`, `query`, `reload`, `start`, `stop`, `update`, `upgrade` (delegates to `updater.main`; the shim above is the supported path), `backup list|prune`, the hidden `record-upgrade <json>` (opens the DB directly, writes the `upgrades` row; called by the orchestrator as the new code), and `--version`. `list` prints `tfs <version> (<hash>)` first (the daemon's own when it answers). `_open_backend` and `list`/`start`/`stop`/`reload`/`backup prune` refuse while `Lock(root).holder().upgrade` is set. Client-first: `_client()` turns an unreadable config/token into `ControlUnavailable` too, so `list`/`query` fall back to loading `script/` in-process / opening the DB directly (refused on a network mount: `is_network_path`); `reload` needs the daemon; `stop` falls back to the pid in `.tfs/lock` **only when the lock's hostname is this host** (SIGTERM on POSIX; `taskkill /F` on Windows, reported as "forced"), and waits `stop_timeout_seconds + 5` by default; `start -d` refuses when a daemon already answers, re-launches `python -m tag_file_system.cli --root <root> start` detached and polls `/health` for up to 15 s, failing with the tail of `.tfs/daemon.out` if the child dies. `query` validates `--under` (root-relative dir) and blank `--tag` (exit 2); `--mime image/*` is a family match. `list` prints the daemon's per-script load problems (`Daemon.load_problems()`, fed by the loader's `report`). `Daemon(apply_logging=True)` (set by `tfs start`) makes `reload` re-apply `[logging]`; `/health` reports `"stopping"` once a stop is requested; a final `reconcile()` runs after the watch loop ends so events queued behind a long handler are not lost.

## Gotchas

- Two unrelated `Tag` models: `core/interface/file_metadata.Tag` (`name`, `tag_id`, `time_added` — DB queries) and `core/interface/tag.Tag` (`name` — the parser). Check which one you import.
- `FileMetadata.file_format` is the suffix with its dot (`.txt`), `file_type` without it, `mime_type` separate.
- Run keys are content hashes: two identical files under one `@@` function share a key (the second gets no run); a binding failure is a dead key until `ctx.retry`.
- The runner replaces `sys.stdout`/`sys.stderr` with a pass-through dispatcher and raises the root logger to INFO once per process (needed to capture add-on output); pytest's capture is wrapped, not replaced.
- Long-running SQL from an add-on thread blocks the watch loop (one connection, one lock) — keep add-on DB use short.
- `watchfiles` reports a directory rename as one event for the directory: the daemon reconciles the subtree; nothing is done per child by the watcher.
- Windows and `uv sync`: uv cannot replace a file a running process has mapped, and (verified) the editable reinstall rewrites `Scripts/tfs.exe` whenever `pyproject.toml`'s version changes, while any `tfs` process has `_pydantic_core.pyd` mapped. Hence: the `tfs` script is a stdlib-only shim, the orchestrator syncs with `--no-install-project --inexact` (project metadata stays at the old version until the next plain `uv sync`; `version.py` reads `pyproject.toml` for that reason), and it calls `tfs` as `python -P -m tag_file_system.cli`, never `uv run tfs` (implicit sync). A tag that changes `requires-python` cannot be applied by self-update on Windows; sync by hand.
- On Windows the venv's `python.exe` is a uv launcher whose *child* is the interpreter: `Popen.pid` is never the pid a daemon writes into its lock. Judge daemons by the lock and `/health`, as `_start_detached` does.
- `run_plan` records nothing for a root without a database file, and a root that could not record the upgrade (exit 1, no revert) is a root that needs a human; a foreign-host lock skips the root, a second upgrade marker refuses the whole upgrade.
