# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

TagFileSystem is a per-root daemon: it watches a managed folder, keys every file in SQLite, parses tags out of names (`2024--trip/img--raw.jpg`), reads which add-on handlers apply to a folder from its `.tfsfunctions.yaml` (`photo: {resize: {width: 800}}`), runs those user-written add-ons from `script/` on the files, and records runs, traces, provenance and problems so a human, the `tfs` CLI or later an MCP client can query them. Python 3.12, managed with `uv` (src layout, `uv_build` backend). Every source file starts with `# Code by AkinoAlice@TyrantRey` except empty file.

`DESIGN/` holds the approved designs, one file per release, named `v{A}-{B}-{C}.md` after the version it specifies: `DESIGN/v0-1-0.md` is the v1 design (2026-08-30, shipped in 0.1.0), `DESIGN/v0-2-0.md` is the self-update design (approved and implemented 2026-09-02, shipped in 0.2.0; its closing "Implementation notes" list where the code deliberately differs), `DESIGN/v0-3-0.md` is the daemon lifecycle hooks `on_start`/`on_stop` (approved and implemented 2026-09-02, shipped in 0.3.0), `DESIGN/v0-4-0.md` moves functions out of the name grammar into per-folder `.tfsfunctions.yaml` files (approved and implemented 2026-09-12, shipped in 0.4.0; §12 lists what it replaces in v1, §14 where the code deliberately differs), `DESIGN/v0-5-0.md` is the versioned JSON API (`/api/v1`) and the read-only web dashboard in `Frontend/` (approved and implemented 2026-09-12, shipped in 0.5.0; §9 where the code differs). A design wins over this file for **target** behaviour; this file describes the code **as it is**. Source docstrings cite them in full (`DESIGN/v0-1-0.md §7`); an unqualified `DESIGN §N` below means `DESIGN/v0-1-0.md`. Read the relevant design before changing the name grammar, the functions file, schema, configuration, CLI or run semantics; update both when behaviour changes. `README.md` is the user-facing short version.

## Commands

```bash
uv sync                                   # install deps + editable install (registers the `tfs` script)
uv run tfs init <dir>                     # create a root: <dir>/.tfs/{config.toml, db/, token} + <dir>/script/ + a .tfsfunctions.yaml skeleton
uv run tfs start [-d] [--force]           # read every .tfsfunctions.yaml, reconcile + watch; the log goes to [logging] file, foreground or -d (a detached child's own output — a crash — lands in .tfs/daemon.out)
uv run tfs list | query -t x --json | reload | stop
uv run tfs explain <file> [--json]        # what applies to one file, from which folder's file, and what excluded the rest
uv run tfs migrate [--apply] [--rename]   # 0.3.x @@ folder names -> .tfsfunctions.yaml (dry run by default); --rename strips the markers
uv run tfs ui [--open]                    # the web UI's address, token in the URL fragment; needs the daemon and a built Frontend/dist
uv run tfs --version                      # "0.5.0 (abc1234)": pyproject version + git HEAD of the checkout
uv run tfs update [--json]                # fetch origin's release tags and report; changes nothing
uv run tfs upgrade [--to TAG] [--dry-run] [--yes] [--skip-tests] [--wait SEC]   # DESIGN/v0-2-0.md §7
uv run tfs backup list | prune --keep 3   # the snapshots in .tfs/backups/
uv run ty check src tests                 # type check (must be clean; CI also runs --python-platform linux)
uv run ruff format src tests              # format (CI checks it); run before every commit
uv run pytest -q                          # tests (~3.5 min; every test builds its own temporary root)
cd Frontend && npm ci && npm run lint && npm run format:check && npm test && npm run build   # the web UI (Node 20+): tsc + eslint, prettier, vitest, dist/
```

- Every command takes `--root <dir>`; otherwise the root is discovered by walking up from CWD like git. Every root-scoped command also records its root in the registry (`TFS_REGISTRY` overrides the location).
- Linting/formatting is configured for Trunk (`.trunk/trunk.yaml`: ruff `B,D3,E,F` with `E501` ignored, black, isort profile=black, bandit, markdownlint, prettier). The `trunk` CLI is not installed on this machine.
- Tests: `tests/helpers.py` has `fetch` / `metadata_of` / `tag_of` (assert-narrow `Optional` results so `ty check tests` stays clean). Tests that load add-ons carry a `clean_modules` fixture that drops `tfs_addons.*` from `sys.modules`. Daemon/CLI tests pick a free port and write it into the root's `config.toml`. `conftest.py` points `TFS_REGISTRY` at a per-test file (autouse). `tests/fakerepo.py` builds a git checkout shaped like this project with two release tags (schema 2 and 3) and a bare `origin`; `tests/fake_tools.py` stands in for `uv`, `pytest`, `npm` (a fake build writes `Frontend/dist/index.html` holding the release marker; scenario `npm_fail` lists the markers whose build fails) and `tfs` (its fake daemon writes a real lock and answers `/health` and `/stop`) so `tests/test_upgrade.py` runs the real orchestrator end to end. Runner tests switch handlers on with `enable(env, folder, "script.handler", **params)` (writes the folder's `.tfsfunctions.yaml` and reloads the store) and drive the runner with `on_file(hook, path, file)` / `on_transition(path, file, previous, content_changed=...)`; daemon tests write the folder file before `startup()` (it is read then, and on `reload()`).

## Versioning

`version` in `pyproject.toml` is `A.B.C`: **A** = major update (an existing root stops loading or loses data, or the CLI breaks), **B** = new behaviour, backwards compatible — a grammar change an existing root survives with a warning included (0.4.0 was one), **C** = changes update (fix, refactor, typo). A typo is a small change, so it is a C: `+0.0.1`. Bumping A resets B and C to `0`; bumping B resets C. Bump it in the same commit as the change it describes, and keep `README.md`'s Versioning section in step. Design documents carry the same numbers: `DESIGN/v{A}-{B}-{C}.md`.

## Architecture (by layer, bottom up)

**Paths and root (`core/paths.py`, `root.py`)** — DESIGN §2. `is_anchored` / `posix_key` / `has_parent_reference` answer path questions for *either* OS flavour. `Root.init(dir)` creates the layout (refuses if the dir, an ancestor or a descendant already has `.tfs/`, or if a file is in the way; cleans up on failure); `Root.discover(start)` walks up (`NotARoot`). `Root.relative(path)` **resolves** the path (symlinks, `..`, 8.3 names, case) and returns a `PurePosixPath` key or raises `OutsideRoot`; `absolute(key)` rejects anchored keys, `..`, and drive-relative `D:x` on Windows; `zone(path)` → `Zone.TFS` (any `.tfs` component, `os.path.normcase`) / `SCRIPT` (first component) / `FUNCTIONS` (a file named `.tfsfunctions.yaml`, `FUNCTIONS_FILE`, anywhere else — watched for drift, never indexed) / `DATA`; `same_name` is the normcase comparison every layer uses for these names. `Lock(root).acquire(force=False, port=None, bind=None)` creates `.tfs/lock` **with content atomically** (temp file + `os.link`; `O_EXCL` fallback), judges staleness by pid on this host (`pid_alive`: never `os.kill` on Windows, access-denied = alive) and by age for other hosts, evicts stale locks by renaming them away, never evicts an unreadable lock younger than 2 s, and gives up after 5 s (`LockHeld` carries the holder's `LockInfo`). `force` takes over a foreign-host lock but raises `LockHeld` for a `LockInfo.is_live_local()` holder — one daemon per root, always. The daemon records the control address it opened (`bind` + `port`) in the lock, so every command reaches *that* daemon even when `config.toml` is edited or broken while it runs. `LockInfo.upgrade` marks the lock as a `tfs upgrade` marker (DESIGN/v0-2-0.md §7 step 3): its pid is the orchestrator's, so it is live/stale like any lock, `LockHeld` says "being upgraded", and `Daemon.startup()` reports a stale one as `lock.stale` mentioning the upgrade marker.

**Configuration (`config.py`)** — `Config` models `.tfs/config.toml`: `[logging] level/file`, `[daemon] bind/port/stop_timeout_seconds/run_warn_after_seconds`, `[remotes]`. `extra="forbid"`, strict numeric fields, `bind` must be an IP, `logging.file` root-relative without `..` or a drive, remotes are **verbatim strings** that must be absolute in either flavour. `loads/load` raise `ConfigError`; `dumps/write` use a small TOML writer. There is no `.env` any more.

**Name grammar (`services/tagging.py`, `core/interface/tag.py`)** — DESIGN §3 as narrowed by DESIGN/v0-4-0.md §2: names carry tags only. `TaggingParser.parse(segment)` parses one directory name or filename stem; `parse_path(root_relative_path, is_file=True)` parses every segment and merges parent-first (tags = union, first occurrence wins). Anchored paths and `..` are errors. `Tag` (frozen, normalized) rejects illegal characters (`: / \ < > | ? * "` and line breaks) and marker text. `@@` is still a registered marker prefix whose factory always refuses, so a 0.3.x `@@func__arg` becomes a `ParseProblem` (P2 `name.parse`, once per path and marker, reported by `runner.report_parse_problems` whenever a file is indexed) and the rest of the name still parses; `__` is plain text. `split_extension` drops the filename suffix unless it contains `--`.

**Functions file (`functions/model.py`, `functions/store.py`)** — DESIGN/v0-4-0.md §3–§5, §8. `load_file(path, folder)` reads one `.tfsfunctions.yaml` (`yaml.safe_load`, utf-8-sig) into a `FunctionsFile` of `Entry(folder, script, handler, args, exclude, order)`; the document skeleton is a pydantic model with `extra="forbid"` (`version` checked by hand first → `FunctionsError("functions.version")`; syntax / not a mapping / unknown top-level key / non-mapping script → `FunctionsError("functions.parse")`, the whole file refused), while a bad *handler block* (not a mapping, malformed `exclude`, non-string parameter name) lands in `FunctionsFile.invalid` as `functions.signature` and the rest still applies; a `null` block is `{}`. `Exclude.parse(raw)` builds a **predicate tree** (§4): `AnyOf`/`AllOf`/`Not` over the leaves `TagIs(names)` and `FilenameMatches(patterns)` (globs `fnmatchcase` on the lowercased name); a YAML list is `any`, a mapping is one node keyed by exactly one of `PREDICATE_KEYS`, a leaf value may be a list ("any of"); `parse_predicate` raises `ValueError` naming the node (`exclude.all[1].not.tag`); an empty `all` is refused. Every node sees a `Subject(name, tags)` — add a field there for a new kind of leaf — and `reason(subject)` returns the branch that held, rendered (`tag draft`, `all(tag big, not(filename *.jpg))`; `any` → first in document order), which is what `tfs explain` prints. `Entry.identity = (script, handler, args_json)`, `display()` = `photo.resize(width=800)` = the run's `slug`. `FunctionsStore(root, loader, report)`: `load_tree()` walks the root (prunes `.tfs` and top-level `script/`), keeps the last-good parse per folder (`""` = root), forgets vanished files, then `rebind()` — validates every entry against the loaded add-ons (`functions.unbound`: no script / no file handler of that name; `functions.signature`: `binding.check` messages), rebuilds `store.problems` (`{severity, kind, message, file}`, what `tfs list` shows) and reports each problem once until it goes away; `effective(key, tags)` → `Effective(applied, suppressed, named)` by walking `chain(folder_of(key))` root-down in document order, `exclude.reason` → `Suppressed(entry, folder, reason)`, identical `identity` deeper down → skipped, `named` = every valid `(script, handler)` in the chain (what suppresses a `tagged` default); `is_current(folder, path)` compares sha256 with the loaded digest (drift); `explain_payload(store, loader, key, tags, known)` is the JSON-safe dict `tfs explain` and `GET /explain` return. `RESERVED_PARAMETERS = {"exclude"}` lives in `binding.py` (a handler parameter by that name is `addon.signature`).

**Persistence (`database/sqlite.py`, `database/migrations.py`, `database/action_store.py`, `core/interface/{database,file_metadata,action}.py`)** — DESIGN §7. `SQLiteBackend.init_database(path, root_dir)` opens one connection (`check_same_thread=False`, WAL, foreign keys) behind an `RLock` (`@transactional` writes, `@locked` reads; nested calls join the outer transaction) and runs `apply_migrations` (`PRAGMA user_version`; `SchemaTooNew`; `MigrationError` for a rootless open of a DB with absolute paths; migration 1 creates all tables, adds `files.mtime_ns`, rewrites `files.path` to root-relative POSIX, soft-deletes rows it cannot key and parks dead duplicates under `.tfs/duplicates/`; migration 2 — DESIGN/v0-2-0.md §9 — adds the `upgrades` table and `action_runs.code_version/code_hash`; migration 3 — `SCHEMA_VERSION = 3`, DESIGN/v0-4-0.md §7 — adds `action_runs.handler` (`''` on older rows, which no function name can equal) and rebuilds `idx_action_runs_key` over `(file_hash, action_name, handler, hook, args_json)`). `SCHEMA_VERSION` must stay a one-line integer literal: `tfs upgrade` reads it out of the target tag with `git show` and a regex. **Paths are stored as root-relative POSIX keys** (`backend.key()`); `TaggedFile.path` is the key, `original_path` the host path. Files/tags semantics: `insert` revives a soft-deleted row in place, `delete` is soft, `modify` renames, `set_file_tags` makes the exact set, queries exclude deleted rows unless asked, `query_files(path_prefix=)` answers "under `2024--trip`", `newest_first`/`limit`/`offset` page it in SQL (`_file_clauses` builds the one `WHERE`; `count_files` takes the same filters for a page's total), `tag_counts()` is every tag with its live-file count, `query_paths(file_ids)` the keys of a set of ids, soft-deleted rows included (chunked `IN`). `ActionStore(backend)` shares the connection and lock: `register_action(name, script_path, script_hash, signature, hooks)` (upsert by `(name, script_hash)` — one row per loaded script version; `signature` and `hooks` are dicts keyed by handler name, `hooks_json` a legacy list is read back as `{"": [...]}`; monotonic `loaded_at`), `find_run`/`start_run` (key `(file_hash, action, handler, hook, canonical args)`; `RunExists` unless `retry_of` names a final run with the same key; every run is stamped with `version.VERSION`/`COMMIT`; `slug` is display text, never parsed), `finish_run` (terminal; `RunAlreadyFinal`), `mark_interrupted`, `add_trace`, provenance (`emitted` beats `observed`, repeated `observed` accumulates `ambiguous`), problems with `delivered_at`, `file_history` (+ `.timeline`), `query_runs(handler=, path_prefix=, limit=, offset=)` + `count_runs` (`_run_clauses`), `query_problems(..., offset=, newest_first=, kind=, action_name=, file_path=, run_id=)` + `count_problems` (`_problem_clauses`; the old positional callers are untouched), `record_upgrade`/`query_upgrades` (`UpgradeRecord`; `tests_*` are `None` when the suite was skipped). `canonical_json` is the only JSON writer (sorted keys, explicit encoder, `TypeError` otherwise, no NaN) — YAML's own types (`int`, `bool`, lists) are key material as they are.

**Add-on API (`action.py`, `addons/binding.py`, `addons/loader.py`)** — DESIGN §4.1–4.2, §4.4, DESIGN/v0-3-0.md §2. `from tag_file_system import action`: `@action.added() / .modified() / .removed(on_move=False) / .tagged("x") / .on_start() / .on_stop() / .crit() .err() .warn() .info()` mark a function (bare `@action.added` is a `TypeError`); `action.TagDir` / `action.Remote` annotate path-valued args. `binding`: parameters after `(path, metadata, ctx)` (2 for problem handlers, 1 — just `ctx` — for lifecycle handlers) are validated per parameter through cached `TypeAdapter`s; `bind(func, args: Mapping, resolver)` binds **by name** (unknown / missing-required / type errors are `BindingError`s; `TagDir`/`Remote` values must be strings and are resolved first; a value that is already typed passes straight to pydantic, a string still coerces), `check(func, args)` lists every problem without resolving paths (what the functions store validates entries with), `by_position(func, raw_args)` keys v1 positional strings by parameter name (only `tfs migrate` uses it); bare `Path`, `async def`, `*args`, positional-only and keyword-only fixed params, and a parameter named `exclude` (`RESERVED_PARAMETERS`) are `SignatureError`s at load. Problem and lifecycle handlers bind nothing: a required parameter beyond the fixed ones is an `addon.signature` problem, since nothing could ever supply it. `AddonLoader.load_all()` execs every `script/*.py` from source into `tfs_addons.<name>` (no `__pycache__`); imports *from* a script (helpers `_x.py`, sibling add-ons) are served by `_ScriptFinder`, last in `sys.meta_path`, which resolves by the importing code's `__file__` to that root's `script/` (nothing on `sys.path`, installed modules are never shadowed, helpers shared within a root and reloaded on change, circular sibling imports resolve like packages). **Handlers are addressed by name** (DESIGN/v0-4-0.md §5): `FileHandler`/`ProblemHandler`/`LifecycleHandler` carry `name` (`__name__`, or the module attribute for a nameless callable), one `FileHandler` per mark of a function, several functions may share a hook, two distinct functions may not share a name (`addon.signature`), a `tagged` function may not take a parameter named `tag`. Lookups: `addon.named(name)` (every mark of that function), `addon.hooks_of(name)`, `loader.handler_for(script, name)`, `loader.handler_marks(script, name, hook)`, `loader.tag_handlers(tag)`. Rules: bad filenames → `addon.filename` (WARN), import failures incl. `SystemExit` → `addon.import` (previous version kept), bad signatures → `addon.signature`, no handlers of any kind → `addon.empty`, store failure → `db.unwritable`. `Addon.describe()` is the single source of what `tfs list` and `/actions` report: `{"name", "script", "script_hash", "handlers": [{"name", "hooks", "signature"}], "problem_hooks"}`; `Addon.signature` / `hooks_by_handler` are the per-handler dicts `register_action` stores; `AddonLoader.lifecycle_handlers(hook)` returns every add-on's `on_start`/`on_stop` handler, ordered by add-on name.

**Runner (`addons/runner.py`, `addons/context.py`)** — DESIGN §4.3, §4.5, §6, DESIGN/v0-3-0.md §4, DESIGN/v0-4-0.md §5–§7. `ActionRunner(..., functions=FunctionsStore)`; `scope(file)` = `functions.effective(key, tags)`. **`on_transition(path, file, previous, content_changed, source, parent, rescope)`** is the one entry point for a live file: it diffs `scope(previous).applied` (the row as it was — old key, old tags) against `scope(file).applied` by `Entry.identity` and fires `on_file(REMOVED, previous, entries=left, moved=True)` (moved out, untagged, newly excluded), `on_tag` for each tag gained, `on_file(ADDED, entries=entered)` and, on a content change, `on_file(MODIFIED, entries=stayed)`; `rescope=True` (start, reload) offers every entry as `added` again unless the content changed — the run key makes finished work a no-op, so a new entry reaches the files it covers. `on_file(hook, path, file, *, entries=None, ...)` runs, per `Applied` entry parent-first, `loader.handler_marks(script, handler, hook)` (`REMOVED` + `moved` → only `spec.on_move`; on `ADDED` also the function's `tagged` marks whose tag the file carries), with `args = entry.args` (+ `"tag"` for a tagged mark) and `slug = display(...)`. `on_tag(path, file, tag)` runs the global `tagged` defaults (`args={"tag": tag}`) minus those the chain `named`, then every applied entry's `tagged` mark for that tag (`args={"tag", **entry.args}`). `on_removed(row, moved)` = `on_file(REMOVED, entries=scope(row).applied)`. `_execute(handler, hook, *, args, slug, ...)`: key `(file_hash, addon, handler.name, hook, args)` first (`find_run` → skip), provenance guard (a file never re-triggers the action that produced it, for `added`/`modified`), `bind(func, args minus "tag", resolve)` — a `BindingError` (unknown remote, ambiguous tagdir: things only run time knows) is a `failed` run + `action.binding` — then `_invoke`, the shared run body: `start_run`, call the handler with stdout/stderr/logging routed into its trace by a **thread-local dispatcher** installed once per process (streams and the root logger level are restored after each run), and finish `ok`/`failed`/`interrupted` with the matching problem. `on_lifecycle(hook)` goes through the same `_invoke` with `path`/`file` `None` and `call=handler.func`: `on_start`/`on_stop` runs are keyed `("", action, handler, hook, {"session": runner.session})` — one uuid per `ActionRunner`, so each handler fires once per daemon session however often it is called, `source` is `lifecycle`, and `ctx.retry` refuses them (`retry.lifecycle` WARN). `ctx.copy/move/write/delete/emit` keep the DB in step (`Indexer`), record `emitted` provenance and hand the produced file to `on_transition` (`source=chain`, `parent_run_id`, depth ≤ 8; a file that had a row gets `modified`); `ctx.tag/untag` go through `on_transition` too, so a tag can move a file across an exclusion. `ctx.spawn` makes the run thread-backed until `ctx.done()`; a dying thread fails the run; `check_overdue` raises `run.overdue` once (never for a lifecycle run: a service started in `on_start` is meant to outlive the threshold); `stop(timeout)` interrupts leftovers (P0). `problem()` records, then dispatches to `loader.problem_handlers` (level and above) with a thread-local recursion guard; problems raised by runs a handler starts are delivered after it returns. `retry` only for failed/interrupted runs whose file exists, at most `MAX_RETRIES` deep; it rebuilds the arguments from `run.args` (never from `slug`) and refuses with `retry.key_changed` when the handler is gone, renamed, or `check` says the arguments no longer fit (a pre-0.4 row, `handler == ''`, included). `ctx.handler_name` names the function a run is calling.

**Daemon (`services/daemon.py`, `services/indexer.py`, `services/control.py`, `core/logger.py`)** — DESIGN §5, §8. `Indexer.index(path)` is the one place a file becomes a row (stat; hash unless `(size, mtime_ns)` match; insert/update; tags = the name's tags plus whatever the previous row carried beyond *its* name). `Indexer.index` returns `None` for a `.tfsfunctions.yaml`: it is never a row. `Daemon(root, control=True)` owns a `FunctionsStore` (its problems reach the log through `runner.problem`, and `load_problems()` = the scripts' + the store's): `startup()` = lock (`lock.stale`/`lock.overridden`), `mark_interrupted` leftovers (`run.interrupted` P0), control server, `load_all`, **`functions.load_tree()`** (after the handlers, which validation needs; before `on_start`, which may look at it), `on_lifecycle(ON_START)`, `replay_undelivered`, `reconcile()`; `run_forever()` feeds `watch(root)` batches to `process_changes()` and ticks `check_overdue`; `shutdown()` = `_stop_addons()` (`on_lifecycle(ON_STOP)`, so a handler can end the run its `on_start` left open), `runner.stop`, control stop, lock release, DB close. `reload()` = config, `_load()`, `load_tree()`, `reconcile()` (so a new entry reaches the files it covers), returns `{"config", "addons", "functions": {"files", "problems"}}`. `_lifecycle_started` gates the hooks: a daemon that never started runs no lifecycle hook, and every `_load` after startup (a script appearing, `tfs reload`) offers `on_start` to whatever is loaded — the run key makes that a no-op for the add-ons that already had their turn; every `_load` and every script unload also `functions.rebind()`. `process_changes` consolidates (deleted > added > modified), routes by zone (`.tfs` ignored, a `.tfsfunctions.yaml` → P2 `functions.drift` once per folder until the next reload and **nothing applied**, `script/` → loader, data → files), detects **moves** (vanished row whose hash matches an added file → `backend.modify`, then `on_transition(previous=the old row)` so the entries it left fire `removed(on_move=True)`), reconciles added directories, hands every indexed file to `runner.on_transition` (`_fire`), and attributes changes seen while runs are in flight as `observed` provenance (+ P2) — lifecycle runs excluded, since one is in flight for the whole session and would make every change ambiguous. `reconcile()` skips a `.tfsfunctions.yaml` (reporting drift when it differs from what was loaded), offers every file with `rescope=True`, retires a row a 0.3.x daemon made of one, and leaves alone a row whose file exists but was never walked — a run's `ctx.copy`/`ctx.write` into a folder `os.walk` had already listed — instead of retiring it as a move of its source. `Daemon.actions_view()` / `explain(key)` are `services/views.py` (`actions_view`, `explain_view` — `source: "daemon"`), the one place the daemon and the offline CLI build what `list` and `explain` show, so the two paths cannot disagree on which add-ons, which problems, or where a file's tags come from (its row when indexed, else its name). `ControlServer(daemon, bind, port, token, ui_dir)` builds its routes table once — the CLI's `/health` (with `version` and `hash`: the code this daemon runs), `/stop`, `/reload`, `/actions` (also `version`/`hash`), `/files`, `/explain?path=` (400 for an anchored, escaping or configuration-file path), plus `Api.routes()` (`/api/v1/...`, see **Web UI** below) — and `_route` serves `/ui...` **before** the token check (`_serve_ui`: a file under `dist` or nothing, `503` while not built) and everything else after `Authorization: Bearer <.tfs/token>`; `BadRequest` → 400, `NotFound` → 404, an unknown `/api/<v>/` names `/api/v1`; bound **exclusively** ## Gotchas

- Two unrelated `Tag` models: `core/interface/file_metadata.Tag` (`name`, `tag_id`, `time_added` — DB queries) and `core/interface/tag.Tag` (`name` — the parser). Check which one you import.
- `FileMetadata.file_format` is the suffix with its dot (`.txt`), `file_type` without it, `mime_type` separate.
- Run keys are content hashes: two identical files in one entry's scope share a key (the second gets no run); a binding failure is a dead key until `ctx.retry`. The key holds the entry's YAML-typed values, so a 0.3.x run keyed `{"width": "800"}` and a 0.4.0 one keyed `{"width": 800}` differ: the first 0.4.0 start re-runs everything once, by design (DESIGN/v0-4-0.md §7).
- Two wiring paths coexist on purpose: an entry in a `.tfsfunctions.yaml` (needed for every `added`/`modified`/`removed` handler) and `@action.tagged("x")` as a global, argument-free default that a folder entry naming the handler takes over. `tag` (on a tagged function) and `exclude` are reserved parameter names.
- `.tfsfunctions.yaml` is read at `start` and `reload` only; editing it under a running daemon is drift, not a change. Tests must write it before `startup()` or call `reload()`.
- `__` is plain text in names now; `@@` still splits markers and is reported. `test_runner.py` builds scope with `enable(env, folder, "script.handler", **params)`, not with directory names.
- The runner replaces `sys.stdout`/`sys.stderr` with a pass-through dispatcher and raises the root logger to INFO once per process (needed to capture add-on output); pytest's capture is wrapped, not replaced.
- Long-running SQL from an add-on thread blocks the watch loop (one connection, one lock) — keep add-on DB use short.
- `watchfiles` reports a directory rename as one event for the directory: the daemon reconciles the subtree; nothing is done per child by the watcher.
- Windows and `uv sync`: uv cannot replace a file a running process has mapped, and (verified) the editable reinstall rewrites `Scripts/tfs.exe` whenever `pyproject.toml`'s version changes, while any `tfs` process has `_pydantic_core.pyd` mapped. Hence: the `tfs` script is a stdlib-only shim, the orchestrator syncs with `--no-install-project --inexact` (project metadata stays at the old version until the next plain `uv sync`; `version.py` reads `pyproject.toml` for that reason), and it calls `tfs` as `python -P -m tag_file_system.cli`, never `uv run tfs` (implicit sync). A tag that changes `requires-python` cannot be applied by self-update on Windows; sync by hand.
- On Windows the venv's `python.exe` is a uv launcher whose *child* is the interpreter: `Popen.pid` is never the pid a daemon writes into its lock. Judge daemons by the lock and `/health`, as `_start_detached` does. The same launcher is why `start -d` (and the fake daemon in `tests/fake_tools.py`) spawns with `CREATE_NO_WINDOW`, never `DETACHED_PROCESS`: a detached launcher has no console, so the interpreter it starts allocates a visible one — a console window popping up on every daemon start, verified on this machine — while a hidden console is inherited by the interpreter and by anything an add-on spawns.
- `run_plan` records nothing for a root without a database file, and a root that could not record the upgrade (exit 1, no revert) is a root that needs a human; a foreign-host lock skips the root, a second upgrade marker refuses the whole upgrade.
- `_serve_ui` runs **before** the token check: keep it file-only (one existing file under `dist`, no listing, no fallback to `index.html` for unknown paths) — anything it answers is public to whoever can reach the port. Content types come from `ui._TYPES` first because Windows' `mimetypes` reads the registry and can call `.js` `text/plain`.
- Every `Daemon(...)` in a test passes `ui_dir=` (a path that does not exist, or a fake `dist`): `default_ui_dir()` is the checkout's real `Frontend/dist`, which a developer may or may not have built.
- `Frontend/` tests use happy-dom, not jsdom: current jsdom needs `require(esm)` (Node ≥ 22.12), and this machine's Node is 22.11. `vite build` does not type-check; `npm run lint` does.
