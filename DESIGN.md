# TagFileSystem — v1 Design

**Status:** approved 2026-08-30, not yet implemented. This document is the target
behaviour; `CLAUDE.md` describes the code as it currently is. Where they differ,
this document wins for anything being built, and `CLAUDE.md` is updated as each
part lands.

## 1. Purpose

A personal, AI-consumable file manager. Tags and functions are written into
directory and file names; functions trigger user-written **add-ons** (Python
scripts) on the files beneath them; everything that happens — tags, runs,
traces, problems — is recorded in SQLite where a human, a CLI, or later an
MCP/API client can query it.

Runs as **one daemon per root**. Primary deployment is Docker on a NAS; Windows
and Linux for development. Every name-level rule below is therefore
Windows-safe (no `:`, `/`, `\`, `<`, `>`, `|`, `?`, `*`, `"` in markers).

## 2. Root layout (git model)

`tfs init [dir]` turns any existing folder into a managed root without moving
anything:

```
<root>/
  .tfs/
    config.toml     # all configuration (replaces .env)
    db/             # system.db (+ -wal/-shm)
    lock            # pid + hostname of the running daemon
    token           # bearer token for the control channel (generated by init)
  script/           # add-ons, one <func>.py per function slug
  ...               # everything else is managed data
```

- Data = the whole root minus `.tfs/` and `script/`. There is no `files/` level.
- `init` refuses if any ancestor directory already contains `.tfs/`.
- The CLI locates the root by walking up from the CWD, like git.
- Only one daemon may run per root. `.tfs/lock` holds pid + hostname; a second
  `start` refuses. A stale lock (dead pid / old age) is overridable with
  `--force`. Two watchers on one root over SMB would corrupt the DB — this is
  the guardrail.

### `config.toml`

```toml
[logging]
level = "INFO"
file  = ".tfs/tag_file_system.log"

[daemon]
bind = "127.0.0.1"     # set to 0.0.0.0 inside Docker and port-map it
port = 7411
stop_timeout_seconds = 30
run_warn_after_seconds = 300   # running longer than this raises P2

[remotes]              # named destinations outside the root (see §4.4)
photos = "/home/photo"
```

`tfs reload` re-reads this file; there is no `tfs remote` command in v1 —
remotes are edited by hand.

## 3. Name grammar

Applied identically to **every directory segment** under the root and to the
**filename stem**:

```
segment := label? marker*
marker  := '@@' func ( '__' arg )*        # function slug + positional args
         | '--' tag                        # plain tag
```

- `func` matches `[a-z][a-z0-9_]*`, split from args on `__`; names and args may
  not start or end with `_`. Function slugs are **normalized to lowercase**
  (SMB/NTFS are case-insensitive, Linux is not).
- `arg` is any run of characters not containing `__`, `--`, `@@`; `.jpg` is a
  valid arg.
- `tag` is normalized as today: lowercase, non-`[\w-]` stripped, hyphens
  collapsed. The old "leading `category:` is dropped" rule goes away because
  `:` is now a parse error.
- Every marker value is Unicode **NFC**-normalized first, so a name typed on
  macOS (NFD) and the same name typed on Windows yield one tag / one call.
- Any of `: / \ < > | ? * "` or a line break inside a marker → parse error →
  P2 `warn`, marker skipped, the rest of the name still parses.
- **Filename extension.** For a file, the extension (what follows the last
  `.`, as `Path.suffix`) is dropped before parsing — *unless* that text
  contains marker syntax (`--`, `@@`, `__`), in which case it is part of a
  marker and the whole name is parsed. So `img--raw.jpg` → tag `raw`;
  `v1.2--beta` → tag `beta`; a *file* named `@@make_copy__.jpg__photos`
  parses like the directory. A marker value that itself ends in a dotted part
  (`photo@@resize__1.5`) is cut at the dot: put markers before the extension.
  Only the *last* dotted part is an extension, so with multi-part extensions
  keep the markers on the label: `archive--old.tar.gz` yields tag `oldtar`,
  `archive--old.tgz` or `old--archive.tar.gz` yield what you meant.
- `parse_path` only accepts root-relative paths: anything anchored (a leading
  `/` or `\`, a drive, a UNC prefix) or containing `..` is an error, not a
  problem — it is a caller bug, never a user's filename.

Example:

```
@@make_copy__.jpg__photos--archive/2024--trip/img--raw.jpg
```

→ tags `{archive, trip, raw}`, functions `[make_copy(".jpg", "photos")]`.

**Inheritance & order.** A file's tags are the union of all ancestor-segment
tags plus its own. Its functions are all ancestor functions plus its own,
executed **parent first, filename last**. Each `(func, args)` pair runs at most
once per file; `@@resize__800/x/@@resize__400/` is two different actions and
both run.

## 4. Add-ons

### 4.1 Discovery & loading

- `script/<func>.py` binds the slug `func`. Every `script/*.py` is imported
  eagerly at `start` (tag-bound handlers can live in any file).
- Filenames must be lowercase (Zen of Python). A non-lowercase file is a P2
  `warn` and is **not loaded**.
- A syntax/import error in one add-on is a P1 `err`; the others still load.
- `script/` is watched: a changed file is **hot-reloaded** (built into the
  engine, not itself an add-on). An in-flight run finishes with the old code.
  `tfs reload` forces the same thing and also re-reads `config.toml`.
- `@@foo` with no `script/foo.py` is a P1 `err` on every file it applies to.

### 4.2 Decorators

```python
from tag_file_system import action

@action.added()                  # file appears under the @@ dir, or is reconciled at start
def run(path: Path, metadata: FileMetadata, ctx: ActionContext, suffix: str, dst: Remote) -> Any: ...

@action.modified()               # content changed (new hash)
@action.removed(on_move=False)   # real deletion always; on_move=True → leaving the @@ dir also fires
@action.tagged("photos")         # file acquires the tag, from any source (name, ctx.tag, API)

@action.crit() / @action.err() / @action.warn() / @action.info()   # problem handlers
def notify(problem: Problem, ctx: ActionContext) -> None: ...
```

- One script may carry several decorated functions, each with its own
  signature.
- File handlers receive `(path, metadata, ctx, *args)`. Args are the slug's
  positional args **coerced by pydantic** from the annotations (`"800"` →
  `800`; `dst: Remote` / `dst: TagDir` resolve paths, §4.4). Defaults allowed.
  Arity or type mismatch → the run is recorded `failed` with a binding error;
  the file is still inserted and tagged.
- The return value of a handler is serialized into `action_runs.result_json`.
- Problem handlers receive their level **and above** (`warn` also sees `err`
  and `crit`). A problem raised *inside* a problem handler is logged only,
  never re-dispatched.

### 4.3 Run completion & threads

- A synchronous handler's run finishes when it returns.
- Add-ons may create threads. `ctx.spawn(fn)` creates a **tracked** thread;
  once `spawn` has been used the run stays `running` until the add-on calls
  `ctx.done()`. Untracked `threading.Thread` is allowed but invisible.
- A run `running` longer than `run_warn_after_seconds` raises P2; `tfs stop`
  waits `stop_timeout_seconds` then marks remaining runs `interrupted` (P0).
- The engine loop itself stays sequential. `SQLiteBackend` keeps one connection
  opened with `check_same_thread=False` and serializes every call behind a
  lock, so `ctx` is safe to use from spawned threads.

### 4.4 Path-valued args

Literal paths never appear in a slug.

- **Inside the root: destinations are tags.** `dst: TagDir` resolves to the
  directory whose own segment carries that tag (`2024--photos/`). Two
  candidate directories → P1, run fails. Portable across machines; visible to
  the AI through the DB.
- **Outside the root: destinations are remotes.** `dst: Remote` resolves via
  `[remotes]` in `config.toml`. Unknown remote → P1. Same idea as a git remote:
  a name for a location you never want to type in a filename.

### 4.5 `ctx` surface

```
ctx.root, ctx.file (TaggedFile), ctx.run_id
ctx.copy / move / write / delete / emit      # file ops, logged + provenance (§6.3)
ctx.resolve(TagDir | Remote)                 # explicit path resolution
ctx.record(**facts)  ctx.log(msg)            # trace entries
ctx.spawn(fn)  ctx.done()                    # threads / completion
ctx.problem(severity, message)               # raise P0–P3 from an add-on
ctx.query(...)                               # read the DB (same filters as tfs query)
ctx.tag(path, *names)  ctx.untag(path, *names)   # write tags → may fire @action.tagged
ctx.retry(run_id)                            # start a fresh run for a failed/interrupted key
```

Raw filesystem calls (`shutil.copy` etc.) are allowed; they are not logged by
construction but are caught as `observed` (§6.3). `ctx.tag` may chain add-ons:
a run started by another run carries `parent_run_id`; chain depth > 8 → P1,
chain stops.

## 5. Engine

- One `watchfiles` watcher on the whole root. `.tfs/` is ignored (SQLite's
  `-wal`/`-shm` writes would otherwise feed back into the watcher); `script/`
  routes to the reloader; everything else routes to the pipeline. Stray files
  at the root are ordinary data.
- **Directory events**: a directory add/rename/delete is one event that says
  nothing about children, yet every child's tags and args changed. Treated as
  "a new folder appeared": the subtree is **rescanned** through the same
  reconciliation code `start` uses.
- **Reconciliation at `start`**: walk the data tree, insert/update every file,
  and start every run whose key (§6.1) has no row. Replaces a separate
  `scan` command.
- **Hashing**: sha256 on first sight and whenever `(size, mtime_ns)` differ
  from the stored row; otherwise the stored hash is reused. `files` stores
  both. A 20 GB video on SMB is not re-hashed because it was touched.
- **Moves**: watchfiles reports delete-at-old + add-at-new. The file keeps its
  hash, so its run keys already exist and nothing re-runs; `removed(on_move=True)`
  handlers are the only ones that notice.

## 6. Runs, provenance, problems

### 6.1 Run identity

```
key = (file_hash, action, hook, args)
```

A run starts **iff no row of any status** has that key. Consequences:

- new or modified file (new hash) → runs
- script edited → **no** automatic re-run; new code applies to future runs
  (avoids re-running a whole folder on every edit)
- `@@` directory renamed (args changed) → every file inside re-runs — a
  deliberate act
- `failed` / `interrupted` keys stay dead until `ctx.retry(run_id)` creates a
  fresh row pointing back via `retry_of`

States: `queued → running → ok | failed | skipped | interrupted`. `queued` is
unused in v1 (the loop is sequential) but reserved so a worker queue later
needs no schema change.

### 6.2 What is captured per run

| Layer | Source | Always? |
| --- | --- | --- |
| Invocation | action, hook, file id + hash, raw slug, `args_json` keyed by parameter name, `result_json`, `script_hash`, timestamps, status, error | yes |
| ctx file ops | `ctx.copy/move/write/delete/emit` → trace + provenance edge | yes when used |
| Captured output | the add-on's `logging` and stdout/stderr, one trace entry per line | yes |
| Declared facts | `ctx.record(**facts)` | when used |
| Observed | filesystem changes seen by the watcher while a run is in flight | flagged, low confidence |

### 6.3 Provenance & loops

- `ctx.emit(path)` (and `copy`/`move`/`write`) records *this file exists
  because of run R*. A generated file never re-triggers the action that made
  it. Hash-based run keys are the safety net for outputs written without
  `ctx`.
- `observed` attribution: change seen while exactly one run is in flight →
  attributed to it; several in flight → attributed to all with
  `ambiguous = true`; none → an ordinary user change.

### 6.4 Severity

| Level | Raised by |
| --- | --- |
| P0 `crit` | DB unwritable/corrupt; lock conflict; `script/` unreadable; run `interrupted`; the daemon itself dies |
| P1 `err` | run `failed` (exception); binding error; `@@foo` without `script/foo.py`; add-on import/syntax error; ambiguous `TagDir` / unknown `Remote`; chain depth exceeded |
| P2 `warn` | `observed` side effects; unparseable marker; run over `run_warn_after_seconds`; stale lock overridden; non-lowercase add-on skipped |
| P3 `info` | run ok; file added/tagged — the ordinary feed |

Problems reach the user **only through `@action.crit/err/warn/info` add-ons**
(NAS notifier, email, webhook — whatever the user writes). Every problem is
also persisted (§7) with `delivered_at`; undelivered problems are **replayed**
to handlers at the next `start`, so a P0 that killed the daemon is still heard.

## 7. Schema

Existing tables `files`, `tags`, `tagged_files`, `events` stay. Changes and
additions (types follow the existing conventions: uuid4 text ids, unix-epoch
integer timestamps, JSON in `TEXT` columns queried with `json_extract`):

```sql
-- files: path becomes root-relative POSIX ("2024--trip/img--raw.jpg"); add
ALTER TABLE files ADD COLUMN mtime_ns INTEGER;

CREATE TABLE actions (
  id             TEXT PRIMARY KEY,
  name           TEXT NOT NULL,          -- function slug
  script_path    TEXT NOT NULL,          -- root-relative
  script_hash    TEXT NOT NULL,
  signature_json TEXT NOT NULL,          -- JSON Schema of the handler's args (from pydantic)
  hooks_json     TEXT NOT NULL,          -- ["added","removed",...]
  loaded_at      INTEGER NOT NULL DEFAULT (unixepoch()),
  UNIQUE (name, script_hash)
);

CREATE TABLE action_runs (
  id             TEXT PRIMARY KEY,
  action_id      TEXT NOT NULL REFERENCES actions(id),
  action_name    TEXT NOT NULL,
  hook           TEXT NOT NULL,          -- added | modified | removed | tagged
  file_id        TEXT REFERENCES files(id) ON DELETE SET NULL,
  file_hash      TEXT NOT NULL,
  slug           TEXT NOT NULL,          -- exactly what was on disk: "make_copy__.jpg__photos"
  args_json      TEXT NOT NULL,          -- {"suffix": ".jpg", "dst": "photos"}
  result_json    TEXT,
  status         TEXT NOT NULL CHECK (status IN ('queued','running','ok','failed','skipped','interrupted')),
  error          TEXT,
  source         TEXT NOT NULL,          -- watch | reconcile | retry | chain
  parent_run_id  TEXT REFERENCES action_runs(id),
  retry_of       TEXT REFERENCES action_runs(id),
  started_at     INTEGER NOT NULL DEFAULT (unixepoch()),
  finished_at    INTEGER
);
CREATE INDEX idx_action_runs_key ON action_runs (file_hash, action_name, hook, args_json);

CREATE TABLE action_trace (
  run_id       TEXT NOT NULL REFERENCES action_runs(id) ON DELETE CASCADE,
  seq          INTEGER NOT NULL,
  ts           INTEGER NOT NULL DEFAULT (unixepoch()),
  kind         TEXT NOT NULL,            -- log | fs.copy | fs.move | fs.write | fs.delete | emit | record | observed
  payload_json TEXT NOT NULL,
  PRIMARY KEY (run_id, seq)
);

CREATE TABLE provenance (
  file_id     TEXT NOT NULL REFERENCES files(id) ON DELETE CASCADE,
  run_id      TEXT NOT NULL REFERENCES action_runs(id) ON DELETE CASCADE,
  kind        TEXT NOT NULL,             -- emitted | observed
  ambiguous   INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (file_id, run_id)
);

CREATE TABLE problems (
  id           TEXT PRIMARY KEY,
  severity     TEXT NOT NULL CHECK (severity IN ('crit','err','warn','info')),
  kind         TEXT NOT NULL,
  message      TEXT NOT NULL,
  action_name  TEXT,
  file_id      TEXT REFERENCES files(id) ON DELETE SET NULL,
  run_id       TEXT REFERENCES action_runs(id) ON DELETE SET NULL,
  occurred_at  INTEGER NOT NULL DEFAULT (unixepoch()),
  delivered_at INTEGER
);
```

Variable-arity args are a **document, not columns**: `args_json` is an object
keyed by parameter name (the names come from the handler signature), queried
with `json_extract(args_json, '$.dst')` and indexable by expression if ever
needed.

### Migrations

- `PRAGMA user_version` + an ordered list of migration functions, applied
  inside `init` and `start`. A DB with a version newer than the code refuses to
  open. **Old databases must load.**
- Migration 1: create the new tables; add `files.mtime_ns`; rewrite
  `files.path` from absolute native to root-relative POSIX. Rows whose path is
  not under the root are set to `status = 'deleted'` and reported as a single
  P2 listing them.

### Acceptance queries

The schema is right when these are single queries: *what happened to file X*
(tags, runs, provenance, in order); *what did run R produce*; *which runs
failed since T and why*; *which files under `@@f` have no `ok` run yet*.

## 8. CLI and daemon

Exactly six commands (Typer):

| Command | Behaviour |
| --- | --- |
| `tfs init [dir]` | create `.tfs/`, `script/`, token, empty DB (migrated to current version) |
| `tfs list` | loaded add-ons with hooks and signature; load problems |
| `tfs query -t a -t b [--name s] [--format .jpg] [--mime image/*] [--deleted] [--json] [--runs]` | tags ANDed; table by default, `--json` for machines; `--runs` adds run history |
| `tfs reload` | re-import add-ons, re-read `config.toml` |
| `tfs start [-d]` | reconciliation, then watch. Foreground by default (Docker PID 1); `-d` detaches |
| `tfs stop` | graceful: stop accepting events, wait `stop_timeout_seconds`, mark the rest `interrupted`, exit |

- The daemon exposes a small **HTTP control channel** on `[daemon] bind:port`
  (`/health`, `/stop`, `/reload`, `/actions`, `/files`), authenticated with
  `Authorization: Bearer <.tfs/token>`. This is the seed of the later API/MCP.
- The CLI is **client-first**: it talks to the daemon; if the daemon is down and
  the DB is on a local disk it reads the DB directly; over a network mount with
  no daemon it refuses with a clear message (WAL over SMB/NFS is unsafe).
- `stop` falls back to the pid in `.tfs/lock` when the channel is unresponsive.
- Docker: root mounted as a volume, `bind = "0.0.0.0"` in the container's
  config, port mapped; the token keeps LAN neighbours out.

## 9. Out of scope for v1

MCP/API beyond the control endpoint; undo; `on_left`, `scan`, `rerun`, `remote`
commands; a worker queue (schema already reserves `queued`); enforcing
`ctx`-only file access.

## 10. Delta from the current code

For whoever implements this, the moving parts relative to `CLAUDE.md`:

- `config.py`: the three `pydantic-settings` classes and `.env` are replaced by
  `.tfs/config.toml`; all paths become root-relative.
- `services/tagging.py`: the parser gains `__` args, per-segment parsing over
  the whole relative path, lowercase slug normalization, the illegal-character
  rule, and loses the `category:` prefix rule.
- `pipeline/database.py`: directories are no longer skipped — they trigger a
  subtree rescan; `@@` markers are dispatched to add-ons instead of logged.
- `services/engine.py`: root-based watch with `.tfs/` exclusion and `script/`
  routing, reconciliation, lock file, hot reload, control channel, graceful
  stop.
- `database/sqlite.py`: migrations, new tables, relative paths, `mtime_ns`
  fast path, connection lock.
- New: `action` decorator module, `ActionContext`, add-on loader, problem
  dispatcher with replay, Typer CLI.
