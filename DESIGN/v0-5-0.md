**Status:** approved 2026-09-12; §10 (the Docker image) added and implemented

## 1. Purpose

Everything the daemon records — tags, runs, traces, provenance, problems, the
configuration it loaded — is meant to be *asked*, by a person, by a tool, by an
AI (v1 §1). Today the only surfaces are the `tfs` CLI and five control
endpoints shaped for it. This release adds the general surface and the first
client of it, in that order:

1. **A versioned JSON API**, `GET /api/v1/...`, served by the daemon on the
   control channel it already has. It is the one an MCP server will wrap later,
   so it is designed from the data model, not from screens.
2. **A read-only web dashboard** that uses nothing but that API: browse files by
   tag and folder, one file's history, runs with their traces, the problems
   feed, the add-ons per handler, the loaded `.tfsfunctions.yaml` files, and
   `explain` for a file. Nothing in the browser changes state; the CLI keeps
   `reload`, `stop`, `retry` and the rest.

## 2. The API

### 2.1 Conventions

- **Base path** `/api/v1`. **Additive** changes — a new key, parameter or
  endpoint — stay `v1` and are a C or B bump like any other change; a rename or
  removal is `/api/v2` and a B bump, with `v1` kept for at least one release.
  `GET /api/v1/status` reports `"api": "v1"`.
- **Auth** exactly as v1 §8: `Authorization: Bearer <.tfs/token>` on every
  request, `401 {"error": "missing or wrong token"}` otherwise.
- **GET only.** Other verbs are `405`. `HEAD` and `OPTIONS` are `405` too.
- **Errors** are `{"error": "<message>"}`: `400` for a parameter the endpoint
  rejects, `404` for a resource that does not exist (`no such file: a/b.txt`,
  `no such run: <id>`) or an unknown endpoint, `500` for a handler that raised.
  `/api/<anything but v1>/...` is `404 {"error": "unknown API version; this
  daemon serves /api/v1"}`.
- **Keys with slashes** travel in `?path=<root-relative POSIX key>`, exactly as
  `/explain` takes them; ids in `?id=`. A blank, anchored or escaping path, or
  the configuration file's own name, is `400`.
- **Lists are pages**: `{"items": [...], "total": N, "limit": L, "offset": O}`.
  `limit` defaults to 50, at most 500; `offset` defaults to 0; anything else is
  `400`. The slice is taken in SQL (`LIMIT ? OFFSET ?`); `total` is a sibling
  `COUNT` over the same `WHERE`. `tags` and `upgrades` are bounded sets and take
  no `offset`.
- **Timestamps** are ISO 8601 with an explicit `+00:00`. **Enum parameters**
  (`status`, `severity`) are validated against the code's own enums; `400` lists
  the accepted values. `since` is `datetime.fromisoformat`, a naive value read
  as UTC.
- **Flags** (`deleted`, `newest`, `undelivered`) read `1/true/yes/on` and
  `0/false/no/off/` as v1's `/files` does.

### 2.2 Endpoints

| Path | Query | Answer |
| --- | --- | --- |
| `/api/v1/status` | – | `/health`'s payload plus `"api": "v1"`, `"functions": {"files", "problems"}` (how many configuration files are loaded, how many problems they have), `"ui": {"built": bool, "dist": path or null}` |
| `/api/v1/files` | `tag` (repeatable, ANDed), `name`, `format`, `mime` (exact or `image/*`), `prefix`, `deleted`, `newest`, `limit`, `offset` | a page of files: `path, file_id, hash, status, tags, size, mime_type, added` — v1's `/files` item without `runs`. Oldest first unless `newest` |
| `/api/v1/file` | `path`, `deleted` | the file with `format` and `mtime_ns` added; `404` when there is no row |
| `/api/v1/file/history` | `path` | `{"file", "timeline": [{"at", "kind": "event" \| "run" \| "provenance" \| "problem", "record"}] oldest first, "events", "runs", "provenance", "problems"}` — v1 §7's *what happened to file X* as one answer; `404` when there is no row |
| `/api/v1/file/explain` | `path` | the `/explain` payload of v0-4-0 §9 |
| `/api/v1/tags` | `deleted` (count soft-deleted files too) | `{"items": [{"name", "tag_id", "added", "files": N}] by name, "total"}` |
| `/api/v1/runs` | `path`, `hash`, `action`, `handler`, `status` (repeatable), `since`, `prefix`, `limit`, `offset` | a page of runs, newest first, each with `"path"` (its file's key, or null when the file is gone) |
| `/api/v1/run` | `id` | `{"run", "trace": [...], "produced": [{"path", "kind", "ambiguous", "file_id"}], "problems": [...]}` — v1 §7's *what did run R produce*; `404` |
| `/api/v1/problems` | `severity` (this level and above), `since`, `kind`, `action`, `path`, `run`, `undelivered`, `limit`, `offset` | a page of problems, **newest first**, each with `"path"` |
| `/api/v1/problem` | `id` | one problem; `404` |
| `/api/v1/addons` | – | `/actions`' payload, unchanged |
| `/api/v1/functions` | – | every loaded configuration file, root first: `{"folder", "file", "digest", "error": null \| {"kind", "message"}, "entries": [{"script", "handler", "args", "display", "exclude", "order", "valid", "problem"}], "invalid": [{"ref", "kind", "message"}]}`, and the store's `"problems"` |
| `/api/v1/upgrades` | `limit` | `{"items": [...], "total"}` newest first |

Runs and problems carry `file_id` in the database; the API resolves the paths of
a page in one query, soft-deleted rows included, so a run whose file is gone
still says where it was. Navigating a run's parents and retries beyond the ids
it carries (`parent_run_id`, `retry_of`) is not an endpoint; the client follows
the ids.

The five endpoints of v1 §8 (`/health`, `/stop`, `/reload`, `/actions`,
`/files`) and `/explain` stay exactly as they are: the CLI is their client, and
it must keep working against a daemon of either release.

## 3. The web UI

### 3.1 Pages

A single-page application at `/ui/`: **Status** (the daemon's identity, its
add-ons, runs in flight, the configuration's counts, whether the UI is built,
the upgrade history); **Files** (the tags with their counts on one side,
toggling an ANDed filter; name, folder, deleted and newest filters; a paged
table); **File** (one file: its tags and metadata, *what applies* from
`explain`, then its timeline, newest first, runs linking to their page);
**Runs** (filters by status, script, handler, folder, since; a paged table with
the run's file); **Run** (fields, arguments and result, error, links to its
parent and to what it retried, the trace, what it produced, its problems);
**Problems** (the feed, newest first, filtered by severity, kind, script,
delivery); **Add-ons** (per script, its handlers with their hooks and typed
parameters as `tfs list` prints them, and the load problems); **Functions**
(per folder, its file's entries with their display form and exclusion, the
blocks that did not become entries, and the store's problems).

**Read-only, by construction.** The client has one HTTP function and it only
issues `GET`. There is no button that reloads, retries, tags, edits or stops;
those stay with the CLI, which asks and answers on a terminal a human is
watching.

### 3.2 Getting in

The control channel wants a bearer token on every request, and a browser
cannot send one when a person types a URL. There is still only one auth path:

- `tfs ui` prints `http://<bind>:<port>/ui/#token=<.tfs/token>` (and opens it
  with `--open`). The token is in the **fragment**: a browser never sends a
  fragment to the server, so it never appears in the control server's log.
- The page reads the token from the fragment once, keeps it in
  `sessionStorage`, rewrites the URL to `/ui/#/`, and sends
  `Authorization: Bearer <token>` on every request it makes. A stored token
  survives a reload of the tab, not the closing of it.
- The files under `/ui/` — `index.html`, the built scripts and styles — are
  served **without** a token. They hold no data; every endpoint that answers
  with data stays as protected as it is today. A daemon bound to `0.0.0.0` in
  Docker therefore exposes exactly one new thing to the LAN: the static shell of
  a UI that cannot show anything without the token.
- A `401` from the API is shown as "token rejected — run `tfs ui` again"; the
  stored token is not cleared, since the more common cause is a restarted root
  with a new token.

### 3.3 Serving the files

- The daemon serves `<checkout>/Frontend/dist` at `/ui/`, resolving each
  request to one file under that directory: `/ui` and `/ui/` are `index.html`;
  anything else must name an existing file below `dist` after percent-decoding,
  with no empty, `.`, `..`, backslash, drive or NUL component, and must resolve
  inside `dist` (symlinks included). Anything else is `404`. There is no
  single-page fallback: the app routes in the fragment, so every path the
  server sees is a real file.
- Content types come from a fixed table for the types a Vite build produces
  before `mimetypes` is consulted (Windows' registry can call a `.js` file
  `text/plain`). Files under `assets/` carry Vite's content hash in their name
  and are `Cache-Control: public, max-age=31536000, immutable`; everything else
  is `no-cache`. Every answer is `X-Content-Type-Options: nosniff`.
- A daemon without a built `dist` answers every `/ui...` request with
  `503 {"error": "UI not built: run \`npm ci && npm run build\` in Frontend/"}`
  — a `503`, not a `404`, so "not built" and "no such file" are told apart —
  and `/api/v1/status` says `"ui": {"built": false}`. `dist` is read per
  request: a build that lands while the daemon runs is served at once.

## 4. Build and distribution

- The frontend is one npm project in **`Frontend/`** at the checkout's root:
  React, TypeScript, Vite, vitest; `package-lock.json` committed, `dist/` and
  `node_modules/` ignored. `npm ci && npm run build` produces `dist/`;
  `npm run dev` serves it with the API proxied to the daemon, and the same
  `#token=` handoff signs in. Nothing in the Python package depends on the
  frontend: `uv sync` alone gives a working daemon and CLI, and the test suite
  never needs a build.
- **CI** gains a `frontend` job (Node 22: install, lint, format check, tests,
  build) and the smoke test checks the `503` before and the `200` after a
  build.
- **`tfs upgrade`** (v0-2-0 §7) gains one best-effort step after step 6's
  `uv sync`: when `Frontend/package.json` exists in the target and `npm` is on
  PATH, run `npm ci` and `npm run build` there. A missing `npm`, a failing
  install or a failing build is a **warning** in the report, never a failed
  upgrade and never a revert: the daemon does not need the UI, and a NAS may
  never have Node. A revert rebuilds the same way, so the old code is not left
  beside the new build. Preflight does not require `npm`.

## 5. Persistence

No schema change: `SCHEMA_VERSION` stays **3**. The read side gains what pages
need — `LIMIT`/`OFFSET` and a sibling `COUNT` over the same `WHERE` for files,
runs and problems; every tag with the number of files that carry it; the paths
of a set of file ids in one query, soft-deleted rows included; and problem
filters by kind, script, file and run.

## 6. Security notes

- The token is never part of a URL the server sees, so it is never logged,
  never in a referrer, never in a proxy's access log. It lives in the tab's
  `sessionStorage` and in the `Authorization` header.
- The static files are the only thing served without a token, and they are
  static: the daemon never reads a file outside `dist` to serve them, and
  never serves a directory listing.
- Default `bind` stays `127.0.0.1`. Binding `0.0.0.0` in Docker is a decision
  the operator makes in `config.toml`, as before; what it exposes without the
  token is the UI's shell and nothing else.
- TLS, users, sessions and rate limits stay out of scope: this is a personal
  daemon on a LAN, and a reverse proxy is the place for those.

## 7. Delta from 0.4.x

- `services/api.py` (new): the request helpers that were private to
  `control.py`, the payload builders, and the `/api/v1` handlers.
- `services/ui.py` (new): resolving `/ui/...` to a file under `dist`, content
  types, cache headers, the "not built" answer.
- `services/control.py`: the routes table is built once; `/ui/...` is served
  before the token check, everything else after it as today; `NotFound` →
  `404`; `ControlClient.get`.
- `services/daemon.py`: `Daemon(root, ..., ui_dir=None)` — the checkout's
  `Frontend/dist` by default, explicit in tests.
- `database/sqlite.py`, `database/action_store.py`: paging, counts, tag counts,
  path lookup, problem filters (§5).
- `functions/store.py`: `functions_payload`, the loaded configuration as data.
- `cli.py`: `tfs ui [--open]`.
- `updater.py`: the best-effort frontend build, its warning, the plan line.
- `Frontend/`: the application. `.github/workflows/test.yml`: the `frontend`
  job and the smoke checks. `.gitignore`: `Frontend/node_modules/`,
  `Frontend/dist/`.

## 8. Out of scope

- **Writes from the browser** — reload, retry, tag, untag, editing a
  `.tfsfunctions.yaml`. Each needs its own answer to "what if the watcher and
  the browser disagree", and none is needed to look.
- **Any auth beyond the token**: users, sessions, cookies, TLS. A reverse proxy
  does those better.
- **The MCP server itself.** This release makes it a thin wrapper; writing it is
  the next release.
- **Live updates** (websockets, server-sent events). Every page has Refresh.
- **Packaging the UI into the wheel.** The install is a checkout; `dist` lives
  in it.
- **Run-tree navigation as an endpoint** (children of a run, a retry chain).
  The ids are in the payloads; a client can follow them.

## 9. Implementation notes

Where the code deliberately differs from or narrows the text above, as
v0-4-0 §14.

1. **happy-dom, not jsdom, under vitest.** jsdom's current release pulls in
   a dependency that needs `require(esm)` (Node ≥ 22.12); the development
   machine runs 22.11 and `engines.node` promises `>= 20`. happy-dom works
   on every Node the project supports; nothing in the tests is jsdom-specific.
2. **`npm run build` is `vite build` alone**; `npm run lint` is `tsc --noEmit
   && eslint .`. A type-level nit therefore cannot fail the build `tfs
   upgrade` runs, while CI's `frontend` job still refuses it.
3. **The token survives a storage that throws.** `adoptTokenFromFragment`
   keeps a module-level copy of what this page load adopted, for a browser
   whose `sessionStorage` is blocked (private mode, a locked-down profile):
   the page works for that load, and only §3.2's "survives a reload" is
   lost.
4. **A run's detail lists its own `run.ok`/`run.failed` record** among its
   problems: `problems` are `query_problems(run_id=)`, and the run's outcome
   is one of them. The Run page shows it as such.
5. **`/api/v1/run` folds "produced by" into `produced`**: every provenance
   edge of the run, `emitted` or `observed`, with the file's path — the
   plan's `produced_by` was the same edges from the file's side.
6. **`/files` gained `newest=1`**; `tags` and `upgrades` have `total` but no
   `offset` (a root has few of either; `upgrades` takes `limit`).
7. **`functions.files` in `/api/v1/status` counts loaded files** — parsed
   and kept, the same number `reload` reports — not folders with a
   file-level error and no last-good parse.
8. **`HEAD` is served for `/ui/...`** (headers, no body); any other verb
   there is 405. The API is GET-only as designed.
9. **A reconcile bug fixed in passing (`daemon.py`)**: a file a run produced
   *during* the reconcile walk (`ctx.copy` into a folder `os.walk` had
   already listed) was soft-deleted at the end of that same walk as a
   "move" of its source — same hash — and revived by the watcher a moment
   later. The API's file and tag counts made the race visible; the delete
   pass now leaves alone any row whose file exists on disk.
10. **The updater resolves `npm` with `shutil.which`** (so `npm.cmd` is found
    on Windows and a test can inject a Python path); the build's warning is
    printed when it happens *and* counted in the closing line (`upgraded to
    X, with 1 warning(s)`); `print_plan` says whether it will try. The
    `frontend` CI job and the smoke checks pin Node 22.
11. **The smoke test reads the daemon's port from `.tfs/lock`** (the address
    the daemon actually opened) rather than `config.toml`, and drives the
    checks with `curl`.
12. **`Frontend/package.json` runtime dependencies** are exactly `react`,
    `react-dom`, `react-router-dom` (React 19, React Router 7 at
    implementation time; the lockfile pins them). `Frontend/dist` and
    `node_modules` are ignored; `Frontend/coverage` too, for a future
    `vitest --coverage`.
13. **The container's healthcheck says "ok" before the first reconcile is
    done** (§10): the control server is up early in `startup()` and
    `/health` answers `ok` for any daemon that is not stopping, so a large
    root is `healthy` while it is still indexing. `started` in the same
    payload says when the reconcile finished.
14. **The image installs the project, not editable**, so `version.repo_dir()`
    is `None` and `VERSION` comes from the installed metadata; the image's
    `pyproject.toml` is copied for the build only. A version bump therefore
    needs `uv lock` before `uv sync --locked` accepts it, in the image as in
    CI.
15. **`.dockerignore` is an allowlist**: a new build input has to be added
    there (`!path/`) or the `COPY` fails.
16. **`stop_grace_period` is compose's**, not the image's: the Dockerfile
    sets no `STOPSIGNAL` and relies on Docker's default SIGTERM.
17. **§11: the rate limiter's bucket starts full.** `max_runs_per_minute =
    60` lets the first 60 starts through at once and paces from there; a
    limit that must bite from the first run is a smaller bucket. The
    token test carries a `1e-9` epsilon (30 refills of `2/60` sum to
    `0.999…`), and a pause is never shorter than 1 ms.
18. **§11: the queue is FIFO through a nested drain.** In inline mode an
    item that reconciles a directory drains what was queued *before* the
    items it produced first; nothing waits on anything, so the order only
    shows in tests.
19. **§11: `plan` lists only the files with something to say** (a
    candidate that would run, a stale run, an entry leaving); the counts
    are always over every file examined. Offline, `functions` reports each
    file as `loaded` and `scripts` carry no `state`: nothing is loaded to
    compare with. A `newly included` reason also covers an entry whose
    arguments changed while its exclusion went.
20. **§11: what the file commands answer.** `applies` is every applied
    entry's `display()` (a `tagged` handler a folder names included);
    `rerun` reports `candidates` (marks) beside `files`; `remove` answers
    the keys it retired. `tfs doctor` adds a `mount` check (a root on a
    network mount) and a `ui` line the table does not list. `tfs status`
    offline lists runs `ok`/`failed`/`interrupted`/`left open` from the
    database.
21. **§11: a reload refused by the threshold still reloads `config.toml`**
    (so a raised `confirm_above` takes effect) and records P2
    `reload.refused`; the scripts are not re-imported either — the plan
    was computed against the loaded ones.

## 10. The Docker image

Added 2026-09-15, in the 0.5.0 release. v0-1-0 §1 named Docker on a NAS as
the primary deployment and §8 said how: the root as a volume,
`bind = "0.0.0.0"`, the port mapped. Nothing shipped it. There was no image,
and a daemon installed any way but as a git checkout had no web UI
(`default_ui_dir` was `<checkout>/Frontend/dist` or nothing), no commit to
report, and no log on its console. This section ships the image and the
compose file, and turns the three things the daemon assumed about a checkout
into explicit inputs.

### 10.1 What ships

- **`Dockerfile`** at the checkout's root, two stages: `node:22-alpine`
  builds `Frontend/dist`; `python:3.12-slim-bookworm` with uv installs the
  locked dependencies and the project itself (not editable) into
  `/app/.venv`, copies the UI to `/app/ui`, and runs as user `tfs`
  (1000:1000) with `/data` as the working directory. No git, no checkout, no
  dev dependencies, no tests inside.
- **`docker-compose.yml`**: one service `tfs`; the root at `./data`
  (`TFS_ROOT`), port `7411` published (`TFS_PORT`), `user: PUID:PGID`,
  `init: true`, `restart: unless-stopped`, `stop_grace_period` 45 s.
  `.env.example` lists every knob.
- **`docker/`**: `entrypoint.sh`, `healthcheck.py`,
  `requirements-addons.txt` (§10.3).
- **`.dockerignore`** as an allowlist (the build context is exactly what the
  Dockerfile copies), **`.gitattributes`** keeping LF on the files the
  container runs.
- **CI**: a `docker` job that builds the image and runs the container through
  the same checks as the smoke test (§10.5).

### 10.2 The daemon outside a checkout

Three environment variables, read by the code; nothing else changes:

| Variable          | Read by                        | Meaning                                                                                                                                                                                                        |
| ----------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `TFS_UI_DIR`      | `services/ui.default_ui_dir()` | Where the built UI is. Beats the checkout's `Frontend/dist`; blank is unset. The image sets `/app/ui`.                                                                                                        |
| `TFS_COMMIT`      | `version.COMMIT`               | The commit the code came from, a full 40-hex hash, consulted only when there is no checkout (a checkout's `HEAD` always wins). Anything else is "unknown", never a guess. The image sets it from `GIT_COMMIT`. |
| `TFS_LOG_CONSOLE` | `tfs start --log-console`      | The flag as an environment variable (Typer's `envvar`), for a service manager (§10.3).                                                                                                                         |

`TFS_REGISTRY` (v0-2-0 §5) already existed; the image points it at
`/tmp/tfs/roots.json`, since the registry serves `tfs upgrade`, which has
no meaning in a container (§10.4).

### 10.3 The container contract

- **The root is `/data`**, one per container, mounted from the host. A first
  start with no `.tfs/config.toml` runs `tfs init /data` and sets
  `[daemon] bind` to `0.0.0.0` (`TFS_BIND` overrides): the loopback `tfs
  init` writes is unreachable through a published port. A later start that
  finds `bind = "127.0.0.1"` warns and goes on; the operator may have chosen
  it. Nothing else in the root is ever edited by the image.
- **`tfs start --log-console`** is the command: the log goes to
  `[logging] file` as always *and* to stdout, which is what `docker logs`
  and a service manager collect. It is a foreground option (`-d` with it is
  a usage error, exit 2), and `reload` re-applies `[logging]` the same way.
- **Signals.** The daemon already stops cleanly on SIGTERM (v0-1-0 §5).
  `init: true` puts tini at pid 1, so the signal is forwarded and whatever
  add-ons spawn is reaped; the entrypoint `exec`s the command so the daemon
  is tini's direct child. `stop_grace_period` must exceed
  `stop_timeout_seconds`: past it Docker sends SIGKILL, in-flight runs are
  `interrupted` at the next start, and the lock is left behind.
- **The lock and a restarted container.** `.tfs/lock` holds the daemon's
  pid and hostname (v0-1-0 §2). A container's hostname is its id and its
  pids start over at every start, so a lock left by a SIGKILL looks *live*
  to the next daemon in the same container whenever that pid is in use
  again, and `--force` refuses a live local lock by design. The entrypoint
  therefore removes a lock stamped with **this container's own hostname**
  before the command runs: the pid namespace began with this process, so
  nothing in it can hold that lock. A lock from any other hostname (a daemon
  on the NAS itself, an earlier container that was replaced rather than
  restarted) is left for the daemon to judge by its own rules: stale after
  `DEFAULT_STALE_AFTER_SECONDS`, `--force`, or the operator deleting it once
  sure that daemon is gone. One daemon per root still holds: do not run
  `tfs start` on the host for a root a container manages.
- **Health.** `HEALTHCHECK` runs `docker/healthcheck.py` every 30 s:
  `GET /health` on the address recorded in the lock with the root's token,
  healthy only for `"status": "ok"` (`"stopping"`, no lock, no answer are
  unhealthy). Standard library only.
- **The user.** The image's `tfs` user is 1000:1000; compose overrides it
  with `PUID:PGID` so the files the daemon creates (`ctx.copy`, `ctx.write`)
  belong to whoever owns the root. The root must exist and be writable by
  that uid before the first start (Docker creates a missing bind-mount source
  as root); the entrypoint says so and exits 1 when it is not.
- **Add-on dependencies.** Add-ons are the user's Python and may import
  anything. `docker/requirements-addons.txt` (shipped empty, commented) is
  installed into the image's environment at build time; a change means a
  rebuild. Mounting site-packages or installing at start is out of scope:
  the image is immutable, the root is the data.
- **Remotes.** A `[remotes]` target is a path inside the container: mount it
  (`/srv/photos:/remotes/photos`) and name the container path in
  `config.toml`.
- **Watching a mount.** inotify works on a bind mount from a local
  filesystem. It does not on NFS or SMB, nor for Windows/macOS host paths
  under Docker Desktop; watchfiles recognises the WSL kernel Docker Desktop
  runs on and polls on its own, and `WATCHFILES_FORCE_POLLING=true`
  (watchfiles' own switch, passed through by compose) forces polling for
  network mounts. Reconcile at start and `tfs reload` catch up either way.
- **Ports.** The container side is `[daemon] port` (7411 unless the config
  is edited); `TFS_PORT` is the host side. The token is the only protection
  (§6): publish the port on a LAN, never on the internet without a reverse
  proxy.

### 10.4 Upgrades

`tfs update` and `tfs upgrade` (v0-2-0) act on a checkout; in a container
there is none, and `tfs upgrade` fails at preflight. Upgrading a container is
`git pull && docker compose up -d --build`: the old container stops cleanly
(SIGTERM, the lock released), the new one runs the new code, and the schema
migrates at its first start as any start does. v0-2-0 §9's snapshots belong
to `tfs upgrade`: back up `.tfs/db/` yourself before a release that changes
`SCHEMA_VERSION`. `upgrades` rows are written by `tfs upgrade` only; a
container upgrade leaves none.

### 10.5 CI

A `docker` job (Linux): build the image with the commit as `GIT_COMMIT`,
start it with compose on a fresh root as the runner's uid, wait for
`healthy`, then check that `/health` reports that commit, `/ui/` is 200,
`/api/v1/status` says `built: true`, a file dropped into the root is found by
`tfs query` through `docker compose exec`, `tfs ui` prints the address, and
the console carries the log; then that a clean stop releases the lock, a
`kill` leaves it, and the restarted container removes it and comes back
healthy.

### 10.6 Delta

- `services/ui.py`: `UI_DIR_ENV`, `default_ui_dir(environ)`.
- `version.py`: `COMMIT_ENV`, `commit_from_env(environ)`; `COMMIT` falls
  back to it outside a checkout.
- `cli.py`: `start --log-console` (`TFS_LOG_CONSOLE`), refused with `-d`;
  `services/daemon.py`: `Daemon(log_console=)`, and `reload()` re-applies
  `[logging]` with it.
- New: `Dockerfile`, `docker-compose.yml`, `.env.example`, `.dockerignore`,
  `.gitattributes`, `docker/`; the `docker` CI job.
- No schema change: `SCHEMA_VERSION` stays 3.

### 10.7 Out of scope

- **Publishing the image** to a registry on a release tag. The image is
  built from the checkout; a registry is the next step once the tag-to-image
  mapping is decided.
- **TLS, a reverse proxy, users.** As §6: a LAN service behind a token.
- **Several roots in one container.** One daemon per root (v0-1-0 §1); run
  one service per root, each with its own port and volume.
- **A lock that survives pid reuse** (recording the process start time in
  the lock) would make the entrypoint's rule unnecessary everywhere, not
  just in Docker; it changes the lock format `updater.py` mirrors, so it
  waits for a release of its own.

## 11. Operations: plan, work control, status, doctor, file commands

Added 2026-09-16, in the 0.5.0 release. The daemon runs what the tree says,
the moment it says it: a `.tfsfunctions.yaml` edit followed by `tfs reload`
starts every run the new entries ask for, on every file they cover, with no
way to see that list first, no way to hold it back, slow it down, bound it,
or stop one run once it has started. This section adds the operator's
controls. The first of them governs the rest: **`tfs plan` must answer,
before `tfs reload`, which handlers would run on which files, and why.**

### 11.1 Commands

| Command                                              | Does                                                                                                                                                                                                                        |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tfs plan [PATH] [--all] [--json]`                   | What `tfs reload` would start (§11.2): per file, the handlers that would run and why; the ones already run; the entries a file leaves; how each `.tfsfunctions.yaml` and each script differs from what the daemon loaded.   |
| `tfs status [--json]`                                | The daemon in one screen (§11.5): running/paused/stopping, uptime, queue depth, runs in flight, the limits in force, files, failed runs, undelivered problems, drift. Offline: the lock and the database's counts.          |
| `tfs doctor [--json]`                                | Checks the root, the configuration, the token, the database, the lock, the daemon and its version, the scripts, the functions files, drift, failed runs, free space; `ok`/`warn`/`fail` per check, exit 1 on a `fail`.    |
| `tfs pause` / `tfs resume`                           | Stop starting runs / start them again (§11.3). Watching and indexing go on; the work queues.                                                                                                                                |
| `tfs retry RUN_ID`                                   | A fresh run for a failed or interrupted run, under its own key (§11.3, retry).                                                                                                                                              |
| `tfs rerun --handler S.H [PATH] [--failed] [--stale] [--dry-run] [--yes]` | Run handler `H` of script `S` again on the files in its scope, finished runs included; `--failed` only where the last run failed, `--stale` only where it ran with an older script; `--dry-run` counts.                    |
| `tfs cancel RUN_ID`                                  | Stop a run in flight (§11.3, cancel).                                                                                                                                                                                       |
| `tfs reload [--yes]`                                 | As before; refuses when the plan exceeds `confirm_above` (§11.3, threshold) unless `--yes`.                                                                                                                                 |
| `tfs touch PATH [--content TEXT]`                    | Create a data file (or update its mtime) inside the root (§11.6).                                                                                                                                                           |
| `tfs cp SRC DST` / `tfs mv SRC DST`                  | Copy / move a data file; `DST` may be a directory.                                                                                                                                                                          |
| `tfs rm PATH [-r]`                                   | Delete a data file, or a directory with `-r`.                                                                                                                                                                               |
| `tfs mkdir PATH`                                     | Create a directory (its name's tags are what files placed there will carry).                                                                                                                                                |

Every one of them is client-first (v0-1-0 §8): through the running daemon,
whose loaded state is what runs; offline where the section says so, against
the files and the database as they are.

### 11.2 The plan

`tfs plan` computes what a `tfs reload` would do, without doing it. The
inputs are the add-ons as loaded, the `.tfsfunctions.yaml` tree **as it is
on disk** (a second `FunctionsStore`, read for the answer and thrown away —
the daemon's own store is untouched), the tree the daemon **has loaded**
(daemon only), the file rows, and the runs.

For every live row under `PATH` (a file, or a directory as a prefix; the
whole root by default) — the daemon has not indexed a file the watcher has
not delivered yet, and the plan does not stat the tree — the plan takes
`effective(key, tags)` under the on-disk tree and, for each applied entry,
the marks that `on_file(added)` would run at a reload: the handler's `added`
marks and its `tagged` marks whose tag the file carries (v0-4-0 §5, §6:
reload is a *rescope*, so `modified` and `removed` do not fire). Each mark
is one candidate, keyed `(file hash, script, handler, hook, arguments)`
exactly as the runner keys it, and the store answers:

- **would run** — no run has the key. The reason, from what the daemon
  loaded: `new entry from photos/.tfsfunctions.yaml` (nothing applied this
  `script.handler` to the file before), `arguments changed from
  photo.resize(width=600)` (the same handler applied with other
  parameters), `newly included: was excluded by tag draft` (the identity
  was in the file's `suppressed` before), or `never ran` (the entry applied
  before and no run exists — the entry is new since the file's last
  reconcile, or a start never got to it). Offline there is no loaded tree;
  the reason then comes from the run history alone: `arguments changed:
  last ran as photo.resize(width=600)` when a run of the same handler and
  hook exists on the file with other arguments, else `never ran`.
- **skipped** — a run has the key: `already ran: ok at <time>`, `failed at
  <time>` (a failed run holds its key as any run does; `tfs retry` is the
  way past it), `in flight`; or the provenance guard holds (`produced by
  photo`: a file an add-on made never re-triggers it, v0-1-0 §6.3).
- **stale** — the run that holds the key was made by a script whose hash
  differs from the loaded script's (`actions.script_hash` of the run's
  `action_id` against `Addon.script_hash`): the code changed, the key did
  not (v0-4-0 §7). Reported, never re-run on its own; `tfs rerun --stale`
  is the explicit way.
- **leaving** (daemon only) — an entry applied to the file under the loaded
  tree and not under the on-disk one: `entry removed from <file>`, `now
  excluded by <reason>`, `<file> no longer loads`. A reload fires no
  `removed` for these (it is a rescope, not a move); the plan says so.

The summary counts files examined, candidates that would run, already ran,
stale and leaving, and the same per `display` and hook (`photo.resize(width=800)
added: 250 file(s)`). Two more sections make the **impact of an edit**
visible before it is applied:

- **functions files** — every folder's file in the union of loaded and
  on-disk: `unchanged`, `changed` (with the entries added and removed, by
  `display`), `new`, `gone`, or `error` (the file on disk does not parse;
  at reload the loaded version stays in force, §8 of v0-4-0);
- **scripts** — every `script/*.py`: `unchanged`, `changed` (loaded hash vs
  on-disk hash: reload re-imports it; existing runs keep their keys), `new`
  (not loaded yet), `gone`.

The plan closes with the threshold verdict: the number that would run
against `[daemon] confirm_above` (§11.3), and whether `tfs reload` will
refuse without `--yes`.

Through the daemon the answer is `GET /api/v1/plan?path=|prefix=&limit=`
(`source: "daemon"`); offline `tfs plan` loads `script/` and the tree from
disk (`services.views.load_root`), opens the database directly (refused on a
network mount, as `tfs query` is) and computes the same view with no loaded
tree to compare against (`source: "disk"` — what the next `tfs start` would
run, since a start loads exactly what is on disk). `limit` bounds the files
listed (default 200, at most 5000; `--all` in the CLI); the counts are always
over every file.

### 11.3 Work control

**The queue.** The daemon owns a work queue (`services/work.py`). What the
watcher, a reconcile, `tfs retry`, `tfs rerun` and the file commands
produce is no longer run on the spot: it is an *item* — a file transition
(`on_transition` with the row it replaced), a removal, a retry, a rerun —
put on the queue and executed by `[daemon] max_concurrent_runs` worker
threads (default 1). Runs chained by a handler (`ctx.copy` → the copy's
own handlers) stay inside the run that caused them, as today: a worker
executes an item to its end, chains included. Lifecycle hooks and problem
handlers never queue; they are not file work. `max_concurrent_runs = 0`
runs every item on the thread that produced it — the watch loop — which is
what 0.4.x did; the test suite runs that way except where it tests the
workers.

An item is re-validated when a worker takes it: the file is stat-ed, and
when its size or mtime differ from the row the item was made with, it is
indexed again and the transition runs against the file **as it is now**,
against the row the item recorded as *previous* — so a run is keyed by the
content the handler sees, never by a hash that is already history. A file
that is gone by then is dropped: its deletion is an item of its own,
behind it in the queue.

**Pause / resume.** `tfs pause` stops the workers taking items; nothing
already running is touched, and the watcher keeps indexing so the rows stay
true. `tfs resume` lets them go on. `/health` reports `paused`; `tfs
status` shows the depth. Pausing is a session state: a restart starts
running. On `tfs stop` the queue is dropped — the next start's reconcile
offers every file again, and the run key makes finished work a no-op.

**Rate limit.** `[daemon] max_runs_per_minute` (default 0, unlimited) is a
token bucket the runner drains before *every* run start that is not a
lifecycle hook, chained runs included: a handler that fans out into many
files is paced like everything else.

**Timeout.** `[daemon] run_timeout_seconds` (default 0, none) ends a file
run that has been in flight longer: the run is `failed` with `timed out
after Ns` and P1 `run.timeout`. Python cannot stop a thread, so the worker
that is stuck in the handler is *abandoned* — flagged so it exits once the
handler returns, its result discarded — and a replacement worker starts. A
thread-backed run (`ctx.spawn` … `ctx.done()`) is finished the same way;
its threads are left to end. `run_warn_after_seconds` stays the P2 it was.
A lifecycle run is never timed out (v0-3-0 §5).

**Cancel.** `tfs cancel RUN_ID` ends a run in flight as `interrupted`
(`cancelled by the operator`, P2 `run.cancelled`), abandoning its worker
as a timeout does. Cancelling is cooperative from the handler's side: the
handle is marked, and the handler's next `ctx` call with a side effect
(`copy`, `move`, `write`, `delete`, `emit`, `tag`, `untag`, `spawn`,
`retry`) raises `action.Cancelled`; `ctx.cancelled` and `ctx.check()` let
a long loop ask. A handler that never calls back runs to its end on the
abandoned thread, and what it wrote stays on disk — the watcher indexes it
like anything else. A run that is not in flight cannot be cancelled (409).
A cancelled run can be retried.

**Retry, rerun, the key.** The run key is the idempotency key (v0-1-0
§6.1): a run starts iff no row of any status has it. Two operations start a
run under a key that has one, and both do it through `retry_of` — the
store's one door for that, open only when the run it names is final:

- `tfs retry RUN_ID` is v0-1-0 §4.5's retry from the terminal: a failed or
  interrupted run gets a fresh run with the same key, arguments rebuilt from
  its own `args`, source `retry`, refused for the reasons `ctx.retry`
  refuses (lifecycle run, file gone, add-on gone, handler renamed or
  arguments no longer fit, retried `MAX_RETRIES` times). The daemon checks
  the reasons before queueing and answers 409 with the one that holds.
- `tfs rerun --handler script.handler [PATH]` walks the files in scope and
  starts, for each candidate exactly as `tfs plan` enumerates them, a run
  with `retry_of` naming the final run that holds the key (an `ok` run
  included) — or a plain run where there is none; source `rerun`. The
  provenance guard is skipped: the operator asked. `--failed` keeps only
  candidates whose run is `failed` or `interrupted` (a bulk retry);
  `--stale` only those whose run was made by an older script; `--dry-run`
  reports the counts and starts nothing. A candidate in flight is skipped.

**Confirmation threshold.** `[daemon] confirm_above` (default 500; 0 turns
it off) bounds the work one operator action may start without a second
look. `tfs reload` computes the plan first and, when more runs would start
than the threshold, reloads `config.toml` and nothing else, answering with
the count; `tfs reload --yes` consents. `tfs rerun` applies the same rule.
A `tfs start` is not bounded: the operator asked for the tree to run, and
`tfs plan` offline shows exactly what that means. The watcher is not
bounded either: files arriving are the daemon's job.

**Code hash.** Every run already records the add-on version that made it
(`action_id` → `actions.script_hash`, one row per loaded script version).
This release surfaces it: the plan and `rerun --stale` compare it with the
loaded script's hash, and `tfs list --json` has carried `script_hash` per
add-on since 0.1.0.

**Races during file changes.** Four are handled, each in one place:

1. *The file changes before its item runs* — the re-validation at dequeue
   above: the run is keyed by what the handler sees. The watcher's own
   event for that change then finds the row already current and does
   nothing.
2. *The handler changes its own input in place* — after the run the runner
   stat-s the input again; when size or mtime moved during the run, it
   records `emitted` provenance of the run on its own file and a trace
   `self_modified`. The watcher's event for that change then meets the
   provenance guard: the add-on that made the content does not re-trigger
   on it, so an in-place `resize` cannot loop. (Before this, the loop was
   broken only when the handler happened to be idempotent.)
3. *Something else changes the file while a run is in flight* — v0-1-0
   §6.3's `observed` provenance and P2, unchanged; the modification is then
   a `modified` event of its own, and runs on the new content.
4. *The file disappears during its run* — the handler fails on its own
   (`FileNotFoundError`), the run is `failed`, retry refuses with
   `retry.file_missing`. Unchanged.

### 11.4 Persistence

No schema change: `SCHEMA_VERSION` stays **3**. `action_runs.status` is
checked by the schema against its six values, so a cancelled run is
`interrupted` with an `error` that says why; `source` is not checked, and
gains `rerun` and `cli`. Provenance and traces are written as before.

### 11.5 Status and doctor

`/health` (frozen shape, additive keys) gains `paused`, `queue` (`depth`,
`active`, `workers`), `uptime_seconds` and `limits` (the four §11.3
settings in force). `/api/v1/status` gains, on top, `files`, `runs`
(`in_flight`, `failed`, `interrupted`), `problems.undelivered`, `drift`
(the folders whose file changed on disk since the load) and `database`
(`schema`, `path`). `GET /api/v1/queue?limit=` lists the items waiting and
the runs in flight. `tfs status` prints these; offline it prints the lock's
state and the database's counts.

`tfs doctor` runs a fixed list of checks and prints one line each,
`ok`/`warn`/`fail` with a detail, exit 1 when any failed:

| Check       | fail                                            | warn                                                                  |
| ----------- | ----------------------------------------------- | --------------------------------------------------------------------- |
| layout      | `.tfs/`, `config.toml`, `token` or `db/` missing | `script/` missing                                                     |
| config      | does not parse                                  | —                                                                     |
| token       | unreadable or empty                             | —                                                                     |
| database    | cannot open, `quick_check` not `ok`, schema newer than the code | schema older (migrates at the next start); on a network mount without a daemon (not checked) |
| lock        | —                                               | stale lock, another host's lock, an upgrade marker                    |
| daemon      | —                                               | not running; reachable but a different version/commit than this CLI (restart to run the new code); paused |
| scripts     | —                                               | every load problem                                                    |
| functions   | —                                               | every configuration problem                                           |
| drift       | —                                               | a file changed since the load (`tfs plan`, then `tfs reload`)         |
| runs        | —                                               | failed or interrupted runs (`tfs retry`, `tfs rerun --failed`)        |
| problems    | —                                               | undelivered problems                                                  |
| disk        | —                                               | less than 1 GB free under the root                                    |
| ui          | —                                               | not built (info only)                                                 |

The daemon-side facts come from `GET /api/v1/doctor` (the database checks,
drift, load problems, runs, free space, as the daemon sees them); offline
the CLI opens the database and checks it itself.

### 11.6 File commands

`touch`, `cp`, `mv`, `rm`, `mkdir` act on **data** paths inside the root:
root-relative or absolute, never `.tfs/`, `script/`, a `.tfsfunctions.yaml`
or anything outside (exit 2). Through the daemon (`POST
/api/v1/files/touch|copy|move|remove|mkdir`) the daemon performs the
operation, indexes the result at once with the `Indexer`, queues the
transition with source `cli`, and answers with the file's row and the
entries that apply to it — so `tfs mv a.jpg 2024--trip/` says which handlers
the move will run. A move is recorded as a move (`backend.modify`, the old
row as *previous*): `removed(on_move=True)` fires for the entries the file
left, `added` for those it entered, exactly as a rename seen by the watcher.
`rm` soft-deletes the row and fires `removed`; `rm -r` does it for every
row below, then removes the tree. `touch` on an existing file updates its
mtime and re-indexes it (no content change, no run). Offline, the commands
do the same on disk and say so: the next start indexes the result (a move
is matched by hash at reconcile, as any rename is).

### 11.10 Out of scope

- **A persistent queue.** Dropped at stop, rebuilt by reconcile: the run key
  makes that safe, and it keeps the database the only state.
- **Per-handler limits and priorities.** One bucket, one pool.
- **Preempting a handler.** Cancel and timeout are cooperative; a handler
  that ignores `ctx` runs to its end on an abandoned thread.
- **Writes from the browser.** §8 stands; the UI shows the queue, it does
  not touch it.
- **`touch`/`mv`/`rm` outside the data zone** (`script/`, `.tfs/`): those
  are the editor's and the shell's.

## 12. Writes from the browser: upload, download, tags

Added 2026-09-17, in the 0.5.0 release. §3.1 made the dashboard read-only
"by construction" and §8 kept writes from the browser out of scope because
each needed an answer to "what if the watcher and the browser disagree".
§11.6 gave that answer for the CLI's file commands — the daemon performs the
write itself, indexes the result at once, queues the transition, and its own
watcher event then finds the row current — and the browser is one more
client of the same API. This section opens three writes to it: putting a
file in, getting a file out, and changing a file's tags. Everything else the
UI shows stays as it was; the UI still never reloads, retries, stops or
edits a `.tfsfunctions.yaml`.

### 12.1 Endpoints

| Method | Path                     | Query / body                                    | Answer                                                                                                     |
| ------ | ------------------------ | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| POST   | `/api/v1/files/upload`   | `path` (the file key to write), `overwrite`; the body is the file's bytes, `Content-Length` required | `{"path", "created", "size", "file", "applies"}`; 409 when the path exists without `overwrite`, 400 for a directory, a missing length, or a body above `UPLOAD_MAX` |
| GET    | `/api/v1/file/content`   | `path`                                          | the file's bytes: `Content-Type` from the row (else `application/octet-stream`), `Content-Length`, `Content-Disposition: attachment; filename=…`; 404 when there is no row or the file is gone |
| POST   | `/api/v1/file/tags`      | `path`; `add`/`remove` repeatable, or a JSON body `{"add": [...], "remove": [...]}` | `{"path", "file", "added", "removed", "kept", "applies"}`; 404 without a row, 400 for an invalid tag name or nothing to do |

`/api/v1/file` gains `name_tags`: the tags the file's own path spells, so a
client knows which of its tags cannot be removed here.

### 12.2 Rules

- **Upload** streams the body into `.tfs/uploads/<uuid>.part` — inside the
  root, so the final `os.replace` is atomic on the same volume, and under
  `.tfs/`, so the watcher and a reconcile never see the half-written file —
  then moves it into place, indexes it and queues the transition with source
  `api`. An existing file is only replaced with `overwrite=1`, and then it
  is a modification: `modified` fires where the content changed. The path
  rules are §11.6's (a data path below the root, never `.tfs/`, `script/`, a
  functions file). The body is bounded by `UPLOAD_MAX` (4 GiB) and must
  carry `Content-Length`; chunked uploads are not accepted.
- **Download** is a `GET` with the same bearer token as every other call,
  answered as the file's bytes. A browser cannot put the token on an `<a
  href>`, and the token never travels in a URL (§3.2), so the page fetches
  the bytes with the header and hands them to the browser as a blob it
  saves under the file's name. The daemon streams the file; it is never
  read into memory whole.
- **Tags** go through the row the way `ctx.tag`/`ctx.untag` do (v0-1-0
  §4.5): `set_file_tags` to the wanted set, then the transition with the
  old row as *previous*, so a gained tag runs its `tagged` handlers and a
  tag that moves the file in or out of an `exclude` fires `added` /
  `removed(on_move=True)`. Tags the file's own name spells are the name's:
  asking to remove one is answered in `kept` and changes nothing (rename
  the file to drop it); they survive a re-index anyway. Names are normalized
  as the grammar normalizes them; an illegal name is a 400.
- **Sources.** Runs these writes start are `source: api`; the CLI's file
  commands stay `cli`.

### 12.3 The UI

- **Files**: an *Upload* box — one or more files, a destination folder
  (defaulting to the folder being browsed), an *overwrite* switch — with
  one line per file: created / replaced / refused and why, and the handlers
  that will run on it (`applies`). The list reloads after.
- **File**: a *Download* button, and the tags as editable chips: an *×* on
  every tag the name does not spell, an input to add one. Each change is
  one request; the page reloads its detail, *what applies* and the history
  after it, so a `tagged` run shows up in the timeline.
- The client keeps one request function per verb shape: `api` (GET JSON),
  `apiPost` (POST JSON), `apiUpload` (POST bytes), `apiBlob` (GET bytes).
  All send the bearer token; all raise `ApiError(status)` on `{"error"}`.

### 12.4 CLI

`tfs tag PATH TAG...` and `tfs untag PATH TAG...` are the same call from a
terminal (daemon only: without the daemon a tag would land in the database
but its handlers would never run, since a start's rescope sees no tag
gained). `untag` says which names it kept because the file's name spells
them.

### 12.5 Delta

- `services/api.py`: `FileResponse`, `file_content`, `file_tags`,
  `files_upload` (a *raw* route: the body is the file), `name_tags` in
  `file_detail`, `_list_param`.
- `services/control.py`: raw routes read the body themselves; a
  `FileResponse` is streamed with its headers; `ControlClient.upload` /
  `download`.
- `services/daemon.py`: `upload`, `content`, `retag`, `UPLOAD_MAX`.
- `core/interface/action.py`: `RunSource.API`.
- `cli.py`: `tag`, `untag`.
- `Frontend/`: `apiPost`/`apiUpload`/`apiBlob`, `UploadBox`, `TagEditor`,
  the Download button.

### 12.6 Out of scope

- **Editing a file in the browser, renaming or deleting it.** `tfs mv` and
  `tfs rm` exist; a delete button is a decision about confirmation flows the
  dashboard does not need yet.
- **Resumable or chunked uploads.** One request per file, bounded.
- **Uploading a folder** (drag-and-drop trees). Files only.
- **Reload, retry, cancel, pause from the browser.** §8 stands for these.
