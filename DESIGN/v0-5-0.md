# TagFileSystem — v0.5.0 Design: a versioned API and a read-only web dashboard

**Status:** approved 2026-09-12. This document is the target behaviour for the
0.5.0 release; `CLAUDE.md` describes the code as it currently is. Where they
differ, this document wins for anything being built — except where the closing
"Implementation notes" (§9) say the code deliberately differs. It extends
[`v0-1-0.md`](v0-1-0.md), [`v0-2-0.md`](v0-2-0.md), [`v0-3-0.md`](v0-3-0.md)
and [`v0-4-0.md`](v0-4-0.md) and replaces nothing: v1 §8's endpoint list
grows, and every endpoint it lists keeps its shape.

## 1. Purpose

Everything the daemon records — tags, runs, traces, provenance, problems, the
configuration it loaded — is meant to be *asked*, by a person, by a tool, by an
AI (v1 §1). Today the only surfaces are the `tfs` CLI and five control
endpoints shaped for it. This release adds the general surface and the first
client of it, in that order:

1. **A versioned JSON API**, `GET /api/v1/...`, served by the daemon on the
   control channel it already has. It is the one an MCP server will wrap later,
   so it is designed from the data model, not from screens.
2. **A read-only web dashboard** that uses nothing but that API: browse files by
   tag and folder, one file's history, runs with their traces, the problems
   feed, the add-ons per handler, the loaded `.tfsfunctions.yaml` files, and
   `explain` for a file. Nothing in the browser changes state; the CLI keeps
   `reload`, `stop`, `retry` and the rest.

## 2. The API

### 2.1 Conventions

- **Base path** `/api/v1`. **Additive** changes — a new key, parameter or
  endpoint — stay `v1` and are a C or B bump like any other change; a rename or
  removal is `/api/v2` and a B bump, with `v1` kept for at least one release.
  `GET /api/v1/status` reports `"api": "v1"`.
- **Auth** exactly as v1 §8: `Authorization: Bearer <.tfs/token>` on every
  request, `401 {"error": "missing or wrong token"}` otherwise.
- **GET only.** Other verbs are `405`. `HEAD` and `OPTIONS` are `405` too.
- **Errors** are `{"error": "<message>"}`: `400` for a parameter the endpoint
  rejects, `404` for a resource that does not exist (`no such file: a/b.txt`,
  `no such run: <id>`) or an unknown endpoint, `500` for a handler that raised.
  `/api/<anything but v1>/...` is `404 {"error": "unknown API version; this
  daemon serves /api/v1"}`.
- **Keys with slashes** travel in `?path=<root-relative POSIX key>`, exactly as
  `/explain` takes them; ids in `?id=`. A blank, anchored or escaping path, or
  the configuration file's own name, is `400`.
- **Lists are pages**: `{"items": [...], "total": N, "limit": L, "offset": O}`.
  `limit` defaults to 50, at most 500; `offset` defaults to 0; anything else is
  `400`. The slice is taken in SQL (`LIMIT ? OFFSET ?`); `total` is a sibling
  `COUNT` over the same `WHERE`. `tags` and `upgrades` are bounded sets and take
  no `offset`.
- **Timestamps** are ISO 8601 with an explicit `+00:00`. **Enum parameters**
  (`status`, `severity`) are validated against the code's own enums; `400` lists
  the accepted values. `since` is `datetime.fromisoformat`, a naive value read
  as UTC.
- **Flags** (`deleted`, `newest`, `undelivered`) read `1/true/yes/on` and
  `0/false/no/off/` as v1's `/files` does.

### 2.2 Endpoints

| Path | Query | Answer |
| --- | --- | --- |
| `/api/v1/status` | – | `/health`'s payload plus `"api": "v1"`, `"functions": {"files", "problems"}` (how many configuration files are loaded, how many problems they have), `"ui": {"built": bool, "dist": path or null}` |
| `/api/v1/files` | `tag` (repeatable, ANDed), `name`, `format`, `mime` (exact or `image/*`), `prefix`, `deleted`, `newest`, `limit`, `offset` | a page of files: `path, file_id, hash, status, tags, size, mime_type, added` — v1's `/files` item without `runs`. Oldest first unless `newest` |
| `/api/v1/file` | `path`, `deleted` | the file with `format` and `mtime_ns` added; `404` when there is no row |
| `/api/v1/file/history` | `path` | `{"file", "timeline": [{"at", "kind": "event" \| "run" \| "provenance" \| "problem", "record"}] oldest first, "events", "runs", "provenance", "problems"}` — v1 §7's *what happened to file X* as one answer; `404` when there is no row |
| `/api/v1/file/explain` | `path` | the `/explain` payload of v0-4-0 §9 |
| `/api/v1/tags` | `deleted` (count soft-deleted files too) | `{"items": [{"name", "tag_id", "added", "files": N}] by name, "total"}` |
| `/api/v1/runs` | `path`, `hash`, `action`, `handler`, `status` (repeatable), `since`, `prefix`, `limit`, `offset` | a page of runs, newest first, each with `"path"` (its file's key, or null when the file is gone) |
| `/api/v1/run` | `id` | `{"run", "trace": [...], "produced": [{"path", "kind", "ambiguous", "file_id"}], "problems": [...]}` — v1 §7's *what did run R produce*; `404` |
| `/api/v1/problems` | `severity` (this level and above), `since`, `kind`, `action`, `path`, `run`, `undelivered`, `limit`, `offset` | a page of problems, **newest first**, each with `"path"` |
| `/api/v1/problem` | `id` | one problem; `404` |
| `/api/v1/addons` | – | `/actions`' payload, unchanged |
| `/api/v1/functions` | – | every loaded configuration file, root first: `{"folder", "file", "digest", "error": null \| {"kind", "message"}, "entries": [{"script", "handler", "args", "display", "exclude", "order", "valid", "problem"}], "invalid": [{"ref", "kind", "message"}]}`, and the store's `"problems"` |
| `/api/v1/upgrades` | `limit` | `{"items": [...], "total"}` newest first |

Runs and problems carry `file_id` in the database; the API resolves the paths of
a page in one query, soft-deleted rows included, so a run whose file is gone
still says where it was. Navigating a run's parents and retries beyond the ids
it carries (`parent_run_id`, `retry_of`) is not an endpoint; the client follows
the ids.

The five endpoints of v1 §8 (`/health`, `/stop`, `/reload`, `/actions`,
`/files`) and `/explain` stay exactly as they are: the CLI is their client, and
it must keep working against a daemon of either release.

## 3. The web UI

### 3.1 Pages

A single-page application at `/ui/`: **Status** (the daemon's identity, its
add-ons, runs in flight, the configuration's counts, whether the UI is built,
the upgrade history); **Files** (the tags with their counts on one side,
toggling an ANDed filter; name, folder, deleted and newest filters; a paged
table); **File** (one file: its tags and metadata, *what applies* from
`explain`, then its timeline, newest first, runs linking to their page);
**Runs** (filters by status, script, handler, folder, since; a paged table with
the run's file); **Run** (fields, arguments and result, error, links to its
parent and to what it retried, the trace, what it produced, its problems);
**Problems** (the feed, newest first, filtered by severity, kind, script,
delivery); **Add-ons** (per script, its handlers with their hooks and typed
parameters as `tfs list` prints them, and the load problems); **Functions**
(per folder, its file's entries with their display form and exclusion, the
blocks that did not become entries, and the store's problems).

**Read-only, by construction.** The client has one HTTP function and it only
issues `GET`. There is no button that reloads, retries, tags, edits or stops;
those stay with the CLI, which asks and answers on a terminal a human is
watching.

### 3.2 Getting in

The control channel wants a bearer token on every request, and a browser
cannot send one when a person types a URL. There is still only one auth path:

- `tfs ui` prints `http://<bind>:<port>/ui/#token=<.tfs/token>` (and opens it
  with `--open`). The token is in the **fragment**: a browser never sends a
  fragment to the server, so it never appears in the control server's log.
- The page reads the token from the fragment once, keeps it in
  `sessionStorage`, rewrites the URL to `/ui/#/`, and sends
  `Authorization: Bearer <token>` on every request it makes. A stored token
  survives a reload of the tab, not the closing of it.
- The files under `/ui/` — `index.html`, the built scripts and styles — are
  served **without** a token. They hold no data; every endpoint that answers
  with data stays as protected as it is today. A daemon bound to `0.0.0.0` in
  Docker therefore exposes exactly one new thing to the LAN: the static shell of
  a UI that cannot show anything without the token.
- A `401` from the API is shown as "token rejected — run `tfs ui` again"; the
  stored token is not cleared, since the more common cause is a restarted root
  with a new token.

### 3.3 Serving the files

- The daemon serves `<checkout>/Frontend/dist` at `/ui/`, resolving each
  request to one file under that directory: `/ui` and `/ui/` are `index.html`;
  anything else must name an existing file below `dist` after percent-decoding,
  with no empty, `.`, `..`, backslash, drive or NUL component, and must resolve
  inside `dist` (symlinks included). Anything else is `404`. There is no
  single-page fallback: the app routes in the fragment, so every path the
  server sees is a real file.
- Content types come from a fixed table for the types a Vite build produces
  before `mimetypes` is consulted (Windows' registry can call a `.js` file
  `text/plain`). Files under `assets/` carry Vite's content hash in their name
  and are `Cache-Control: public, max-age=31536000, immutable`; everything else
  is `no-cache`. Every answer is `X-Content-Type-Options: nosniff`.
- A daemon without a built `dist` answers every `/ui...` request with
  `503 {"error": "UI not built: run \`npm ci && npm run build\` in Frontend/"}`
  — a `503`, not a `404`, so "not built" and "no such file" are told apart —
  and `/api/v1/status` says `"ui": {"built": false}`. `dist` is read per
  request: a build that lands while the daemon runs is served at once.

## 4. Build and distribution

- The frontend is one npm project in **`Frontend/`** at the checkout's root:
  React, TypeScript, Vite, vitest; `package-lock.json` committed, `dist/` and
  `node_modules/` ignored. `npm ci && npm run build` produces `dist/`;
  `npm run dev` serves it with the API proxied to the daemon, and the same
  `#token=` handoff signs in. Nothing in the Python package depends on the
  frontend: `uv sync` alone gives a working daemon and CLI, and the test suite
  never needs a build.
- **CI** gains a `frontend` job (Node 22: install, lint, format check, tests,
  build) and the smoke test checks the `503` before and the `200` after a
  build.
- **`tfs upgrade`** (v0-2-0 §7) gains one best-effort step after step 6's
  `uv sync`: when `Frontend/package.json` exists in the target and `npm` is on
  PATH, run `npm ci` and `npm run build` there. A missing `npm`, a failing
  install or a failing build is a **warning** in the report, never a failed
  upgrade and never a revert: the daemon does not need the UI, and a NAS may
  never have Node. A revert rebuilds the same way, so the old code is not left
  beside the new build. Preflight does not require `npm`.

## 5. Persistence

No schema change: `SCHEMA_VERSION` stays **3**. The read side gains what pages
need — `LIMIT`/`OFFSET` and a sibling `COUNT` over the same `WHERE` for files,
runs and problems; every tag with the number of files that carry it; the paths
of a set of file ids in one query, soft-deleted rows included; and problem
filters by kind, script, file and run.

## 6. Security notes

- The token is never part of a URL the server sees, so it is never logged,
  never in a referrer, never in a proxy's access log. It lives in the tab's
  `sessionStorage` and in the `Authorization` header.
- The static files are the only thing served without a token, and they are
  static: the daemon never reads a file outside `dist` to serve them, and
  never serves a directory listing.
- Default `bind` stays `127.0.0.1`. Binding `0.0.0.0` in Docker is a decision
  the operator makes in `config.toml`, as before; what it exposes without the
  token is the UI's shell and nothing else.
- TLS, users, sessions and rate limits stay out of scope: this is a personal
  daemon on a LAN, and a reverse proxy is the place for those.

## 7. Delta from 0.4.x

- `services/api.py` (new): the request helpers that were private to
  `control.py`, the payload builders, and the `/api/v1` handlers.
- `services/ui.py` (new): resolving `/ui/...` to a file under `dist`, content
  types, cache headers, the "not built" answer.
- `services/control.py`: the routes table is built once; `/ui/...` is served
  before the token check, everything else after it as today; `NotFound` →
  `404`; `ControlClient.get`.
- `services/daemon.py`: `Daemon(root, ..., ui_dir=None)` — the checkout's
  `Frontend/dist` by default, explicit in tests.
- `database/sqlite.py`, `database/action_store.py`: paging, counts, tag counts,
  path lookup, problem filters (§5).
- `functions/store.py`: `functions_payload`, the loaded configuration as data.
- `cli.py`: `tfs ui [--open]`.
- `updater.py`: the best-effort frontend build, its warning, the plan line.
- `Frontend/`: the application. `.github/workflows/test.yml`: the `frontend`
  job and the smoke checks. `.gitignore`: `Frontend/node_modules/`,
  `Frontend/dist/`.

## 8. Out of scope

- **Writes from the browser** — reload, retry, tag, untag, editing a
  `.tfsfunctions.yaml`. Each needs its own answer to "what if the watcher and
  the browser disagree", and none is needed to look.
- **Any auth beyond the token**: users, sessions, cookies, TLS. A reverse proxy
  does those better.
- **The MCP server itself.** This release makes it a thin wrapper; writing it is
  the next release.
- **Live updates** (websockets, server-sent events). Every page has Refresh.
- **Packaging the UI into the wheel.** The install is a checkout; `dist` lives
  in it.
- **Run-tree navigation as an endpoint** (children of a run, a retry chain).
  The ids are in the payloads; a client can follow them.

## 9. Implementation notes

Where the code deliberately differs from or narrows the text above, as
v0-4-0 §14.

1. **happy-dom, not jsdom, under vitest.** jsdom's current release pulls in
   a dependency that needs `require(esm)` (Node ≥ 22.12); the development
   machine runs 22.11 and `engines.node` promises `>= 20`. happy-dom works
   on every Node the project supports; nothing in the tests is jsdom-specific.
2. **`npm run build` is `vite build` alone**; `npm run lint` is `tsc --noEmit
   && eslint .`. A type-level nit therefore cannot fail the build `tfs
   upgrade` runs, while CI's `frontend` job still refuses it.
3. **The token survives a storage that throws.** `adoptTokenFromFragment`
   keeps a module-level copy of what this page load adopted, for a browser
   whose `sessionStorage` is blocked (private mode, a locked-down profile):
   the page works for that load, and only §3.2's "survives a reload" is
   lost.
4. **A run's detail lists its own `run.ok`/`run.failed` record** among its
   problems: `problems` are `query_problems(run_id=)`, and the run's outcome
   is one of them. The Run page shows it as such.
5. **`/api/v1/run` folds "produced by" into `produced`**: every provenance
   edge of the run, `emitted` or `observed`, with the file's path — the
   plan's `produced_by` was the same edges from the file's side.
6. **`/files` gained `newest=1`**; `tags` and `upgrades` have `total` but no
   `offset` (a root has few of either; `upgrades` takes `limit`).
7. **`functions.files` in `/api/v1/status` counts loaded files** — parsed
   and kept, the same number `reload` reports — not folders with a
   file-level error and no last-good parse.
8. **`HEAD` is served for `/ui/...`** (headers, no body); any other verb
   there is 405. The API is GET-only as designed.
9. **A reconcile bug fixed in passing (`daemon.py`)**: a file a run produced
   *during* the reconcile walk (`ctx.copy` into a folder `os.walk` had
   already listed) was soft-deleted at the end of that same walk as a
   "move" of its source — same hash — and revived by the watcher a moment
   later. The API's file and tag counts made the race visible; the delete
   pass now leaves alone any row whose file exists on disk.
10. **The updater resolves `npm` with `shutil.which`** (so `npm.cmd` is found
    on Windows and a test can inject a Python path); the build's warning is
    printed when it happens *and* counted in the closing line (`upgraded to
    X, with 1 warning(s)`); `print_plan` says whether it will try. The
    `frontend` CI job and the smoke checks pin Node 22.
11. **The smoke test reads the daemon's port from `.tfs/lock`** (the address
    the daemon actually opened) rather than `config.toml`, and drives the
    checks with `curl`.
12. **`Frontend/package.json` runtime dependencies** are exactly `react`,
    `react-dom`, `react-router-dom` (React 19, React Router 7 at
    implementation time; the lockfile pins them). `Frontend/dist` and
    `node_modules` are ignored; `Frontend/coverage` too, for a future
    `vitest --coverage`.
