# TagFileSystem — v0.2.0 Design: self-update

**Status:** approved 2026-09-02, not yet implemented. This document is the target
behaviour for the 0.2.0 release; `CLAUDE.md` describes the code as it currently
is. Where they differ, this document wins for anything being built. It extends
[`v0-1-0.md`](v0-1-0.md) and does not replace it: everything that document
specifies still holds.

## 1. Purpose

Move a deployed root from one tagged release to the next without a human at a
shell — safely enough that an unattended NAS can do it, and reversibly enough
that a bad release does not cost you a database.

## 2. Scope

**In scope:** the tool updating itself from its own local git checkout.

**Not in scope:** distribution. There is no PyPI package, no Docker image and no
third-party installer; the only install is a git checkout plus `uv sync`, and
self-update assumes exactly that. Building a public updater before a public
installer is out of order.

**Deferred:** add-on updating. `tfs addon update` / `tfs addon upgrade` (apt's
two-step: refresh, then apply) is a real need, but add-ons in `script/` have no
upstream today and updating them means executing new code someone else wrote —
a materially harder trust model than pulling your own tagged repo. The namespace
is reserved; the design is its own document.

## 3. Version identity

Tags select, hashes record.

- `tfs update` / `tfs upgrade` consider **annotated tags on `origin`**, not the
  tip of a branch. Following `master` would make every work-in-progress commit
  an "available update".
- The **commit hash** is the identity that gets recorded and compared.
- `tfs --version` prints both: `0.2.0 (abc1234)`.
- Version and hash are added to `/health`, to `tfs list`, and stamped on run
  rows, so a result can be attributed to the code that produced it.

Version identity is independently useful and ships first, ahead of the updater.

## 4. Commands

DESIGN §8 of `v0-1-0.md` fixed the CLI at six commands. It becomes:

| Command                                                            | Scope   | Notes                                                                             |
| ------------------------------------------------------------------ | ------- | --------------------------------------------------------------------------------- |
| `tfs update [--json]`                                              | root    | Fetch tags, report, change nothing.                                               |
| `tfs upgrade [--to TAG] [--dry-run] [--yes] [--skip-tests] [--wait SEC]` | root    | The whole sequence in §7.                                                          |
| `tfs backup list`                                                  | root    | What snapshots exist, their size and the tag they came from.                      |
| `tfs backup prune [--keep N] [--dry-run] [--yes]`                  | root    | `--keep` defaults to 3, the same policy `upgrade` applies automatically.          |

Plus one hidden subcommand used only by the orchestrator to write the `upgrades`
row (§9), and `tfs --version`.

Rules:

- `update` and `upgrade` are **root-scoped** like every other command: they take
  `--root`, discover from CWD, and refuse outside a managed root. The install is
  still machine-wide, which is why §5 exists.
- `update` exits non-zero **only on real failure** — an unreachable remote, a
  dirty checkout. "An update is available" is exit 0 with `available: true` in
  `--json`, so a cron wrapper can distinguish "nothing to do" from "could not
  check". `--json` matches the machine interface `query` already established.
- `--skip-tests` skips pytest and **nothing else**. Snapshot, schema warning,
  health check and revert all still run. `--yes` never implies it.
- `tfs clean` is deliberately *not* used for backups; the name stays free for
  unrelated janitorial work (`.tfs/duplicates/`, `__pycache__`).

## 5. Machine state: the root registry

One checkout serves every root on the machine, so upgrading from root A changes
the code root B runs. The updater therefore needs to know every root.

- **Location:** `%APPDATA%\tfs\roots.json` on Windows,
  `${XDG_CONFIG_HOME:-~/.config}/tfs/roots.json` on POSIX.
- **Never `~/.tfs/`.** `Root.discover` walks up looking for `.tfs/`, and
  `Root.init` refuses when any ancestor already has one — so a `.tfs` directory
  in `$HOME` would resolve the home directory as a managed root and make
  `tfs init` fail everywhere beneath it.
- **Written by every root-scoped command** (`init`, `start`, `list`, `query`,
  `stop`, `reload`, `update`, `upgrade`), so roots that predate the feature are
  picked up as soon as they are touched.
- Entries are **hints, not truth**: pruned on read when the path no longer has
  `.tfs/`. A deleted, moved or unmounted root must never fail an upgrade.
- `--dry-run` prints the registry, so "these are the roots I know about" is
  visible before consent rather than inferred afterwards.

This is the first machine-global state the project has ever had; everything else
lives under a root.

## 6. The orchestrator

`tfs upgrade` runs preflight and takes consent on the **old** code, with nothing
touched. It then **copies its own source to a temporary directory and re-execs
there**, and from that point is **standard-library only**.

Both halves of that are load-bearing:

- `git checkout` rewrites `src/` **and** `uv sync --locked` rewrites `.venv`, so
  neither the orchestrator's own modules nor its third-party dependencies are
  stable once the sequence starts. `cli.py` uses function-level imports, so
  "import everything up front" is a discipline one future patch silently breaks.
- The orchestrator's actual work — copy files, run subprocesses, parse JSON, run
  `VACUUM INTO` — is entirely stdlib, `sqlite3` included. A test asserts the
  module imports nothing outside the standard library, so the rule is enforced
  in CI rather than remembered.

Everything else is driven by subprocess: `git`, `uv`, `pytest`, and `tfs` itself.
`cli.py` already launches the daemon this way for `start -d`.

## 7. The upgrade sequence

1. **Preflight** — daemon still running, nothing touched:
   - register this root; read the registry (§5);
   - `.git` exists, tree clean, HEAD on `master` **or** detached exactly at a tag
     from `origin` (this permanently excludes working checkouts, by design);
   - `git --version` and `uv --version` run;
   - `origin` reachable; `git fetch --tags`; target tag resolves;
   - read the target's `SCHEMA_VERSION` with
     `git show <tag>:src/tag_file_system/database/migrations.py` and a regex —
     **never import it**;
   - **refuse** if the target's `SCHEMA_VERSION` is below any registered root's
     `user_version` (a downgrade the daemon would refuse to open anyway);
   - pytest importable unless `--skip-tests`;
   - refuse if runs are in flight — `--wait SEC` drains first, defaulting to
     `[daemon] stop_timeout_seconds`. Never interrupt a run to upgrade: that
     manufactures P0 `run.interrupted` problems as a side effect of maintenance;
   - if the schema changes, print the affected roots and their version deltas and
     prompt `y/N`, defaulting to **no**. When it does not change, say so and skip
     the prompt, so the warning keeps its meaning;
   - `--dry-run` prints the entire plan — target, schema delta, known roots,
     snapshot paths — and exits.

   Every network operation happens here, while the daemon is still serving. A NAS
   that loses its network fails before anything is stopped.

2. **Re-exec** the orchestrator from its temporary copy (§6).

3. **Lock** every registered root's `.tfs/lock` with an upgrade marker. `list`
   and `query` must consult the lock **before** their direct-database fallback
   and refuse, rather than opening the database — see §11.

4. **Stop** the daemons.

5. **Snapshot** each root: `VACUUM INTO .tfs/backups/<utc>-<from-tag>.db`. WAL is
   enabled, so a plain file copy would be a silently incomplete backup. `.tfs/`
   is in `Zone.TFS`, so the watcher ignores the snapshots.

6. `git checkout <tag>` then `uv sync --locked`.

7. **Run the full suite** (unless `--skip-tests`).

8. **Start** the daemon. Migrations run here, on first open.

9. **Poll `/health`.** Compare the reported version string *and* hash against the
   target. The version string is what the message says; the **hash mismatch is
   what fails the upgrade**, because it is the one that cannot be true-but-wrong.

10. **Record** the `upgrades` row (§9) in every affected root, as new code.

11. **Prompt** about this upgrade's snapshots only — default keep, with paths and
    total size shown. Retention keeps the last 3 per root regardless.

Tests run *before* the daemon starts (step 7 before step 8) so the most likely
failure costs a code revert and nothing else.

## 8. Failure and revert

| Fails at            | Recovery                                                             |
| ------------------- | -------------------------------------------------------------------- |
| Preflight (1)       | Nothing touched. Exit non-zero.                                      |
| Checkout / sync (6) | Code revert only. Nothing migrated, so no restore. Daemon restarts.  |
| Tests (7)           | Same as above.                                                       |
| Start / health (8–9)| Code revert **plus** every snapshot restored, all or nothing.        |

Auto-revert fires on hard failure only: import error, process exit, no `/health`
inside 15 s, or a hash mismatch.

If the revert itself fails — the old tag is gone, a snapshot is unreadable, a
disk is full — **stop**. Do not retry, do not loop. Exit non-zero and print the
exact manual steps with the literal tag name and snapshot paths.

A manual `tfs downgrade` is deliberately absent: a second rollback path sharing
no code with the tested one is an untested rollback path, and untested rollback
paths are how the database you were protecting gets lost. Restoring a snapshot by
hand remains the deliberate escape hatch.

## 9. Schema

A new `upgrades` table, written to **every** affected root so each root's history
explains its own schema jump:

- `from_tag`, `from_hash`, `to_tag`, `to_hash`
- `schema_before`, `schema_after`
- `tests_run`, `tests_passed`, `tests_skipped`
- `snapshot_path`
- `outcome`, `started_at`, `finished_at`

Two consequences, accepted knowingly:

- This takes `SCHEMA_VERSION` to **2**, so the first self-update is itself a
  schema change and trips its own warning.
- The row can only be written by the new code after migrating, so a **failed**
  upgrade leaves its evidence in the log and the snapshot, not in the table.

## 10. Platforms and testing

Windows and Linux are both supported; the orchestrator is Python precisely so no
POSIX shell is required. The CI matrix already runs both.

Self-update is the one feature where an untested platform means an unrecoverable
root, so the suite must include, **on both platforms**, a test that fakes a tag,
runs an upgrade, fails the gate, and asserts that code *and* database were
restored.

## 11. Delta from 0.1.x

- `cli.py`: `update`, `upgrade`, `backup list`, `backup prune`, `--version`, one
  hidden record subcommand; `list`/`query` check the upgrade lock before falling
  back to opening the database directly.
- `services/control.py`, `services/daemon.py`: version and hash in `/health`.
- `database/migrations.py`: `SCHEMA_VERSION = 2`, the `upgrades` table.
- New: the stdlib-only orchestrator, the root registry, snapshot and retention.
- **Landable now, independently:** today, with no daemon running, `tfs query`
  falls back to `backend.init_database(...)` (`cli.py:183`, `cli.py:230`) and
  `sqlite.py:140` migrates on every open — so a plain query can migrate a
  production database. The step 3 lock check is its fix, and it is worth
  shipping as a patch release before any of this.
