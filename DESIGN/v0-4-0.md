# TagFileSystem — v0.4.0 Design: functions leave the name grammar

**Status:** approved 2026-09-12, implemented 2026-09-12 (shipped in 0.4.0).
This document is the target behaviour for the 0.4.0 release; `CLAUDE.md`
describes the code as it currently is. Where they differ, this document wins
for anything being built — except where the closing "Implementation notes"
(§14) say the code deliberately differs. It extends
[`v0-1-0.md`](v0-1-0.md), [`v0-2-0.md`](v0-2-0.md) and
[`v0-3-0.md`](v0-3-0.md) and **replaces** the parts of v1 listed in §12:
everything else those documents specify still holds.

## 1. Purpose

In v1 a `@@` marker in a directory or file name did four jobs at once:
**activation** (this add-on applies here), **scope** (to every file beneath,
parent first), **parameters** (positional, split on `__`, bound to the
handler's signature by position) and **run identity** (rename the directory,
every file underneath re-runs).

That is too much for a filename. Positional arguments have no names at the
call site, every value arrives as a string, a typo is invisible until a run
fails, Windows-safe characters limit what an argument may contain, and a
folder cannot be re-parameterised without renaming it — which re-runs its
whole subtree whether or not that was the point.

**Names keep tags. Functions move into a file.** Each folder may carry a
`.tfsfunctions.yaml` naming the handlers that apply to it and below, their
parameters by name, in the types the handler actually wants, with an explicit
exclusion block. A script becomes a *capability* the root provides; the file
is what fires it.

## 2. Name grammar

```
segment := label? marker*
marker  := '--' tag
```

Applied identically to every directory segment under the root and to the
filename stem, exactly as in v1 §3. Tag normalization (NFC, lowercase,
non-`[\w-]` stripped, hyphens collapsed), the illegal-character rule, and
inheritance are **unchanged**: a file's tags are the union of every ancestor
segment's tags plus its own, parent first, first occurrence winning.

What changes:

- **`@@` no longer builds anything.** It remains a registered marker prefix
  whose factory always fails, so an existing `@@make_copy__.jpg__photos/`
  directory becomes a P2 `name.parse` — one unparseable marker, skipped, with
  the rest of the segment still parsed. A root full of v1 names keeps every
  tag it had; it simply stops running functions until its YAML exists (§10).
- **`__` means nothing anywhere.** It was the argument separator and has no
  successor. `split_extension` treats only `--` as marker syntax, so
  `report__final.jpg` is the label `report__final` with extension `.jpg`.
- `ActionCall`, `ParsedPath.actions` and `TaggingParser`'s `actions` target
  field are deleted. `ParsedPath` carries `path`, `tags` and `problems`.

## 3. The file

### 3.1 Shape

```yaml
# ./--tag1/.tfsfunctions.yaml
version: 1
functions:
  photo:                      # script/photo.py
    resize:                   # def resize(...) inside it
      width: 800
      exclude:                # skip the file when any of these holds (§4)
        - tag: tag2
        - filename: test2.jpg
    make_copy:
      suffix: .jpg
      dst: backup
```

Four levels, each with exactly one kind of key, so no user-chosen name ever
collides with a reserved one:

| Level | Key | Value |
| --- | --- | --- |
| document | `version`, `functions` | reserved |
| `functions` | a **script** name — `script/<name>.py`, the existing lowercase slug rule | a mapping of handlers |
| a script | a **handler** name — the Python function's `__name__`, case-sensitive | a mapping of parameters |
| a handler | a **parameter** name from the handler's signature, plus the reserved `exclude` | the value, in YAML's own types |

- **`version` is required** and is `1` for this release. A file declaring a
  version this code does not know is refused (§8) — the rule the database
  already applies to itself (`SchemaTooNew`).
- **Parameters are named and natively typed.** `width: 800` is an `int`
  before pydantic ever sees it; `dst: backup` is the string a `Remote` or
  `TagDir` annotation resolves at run time, so the run key still does not
  depend on how a remote resolves today (v1 §4.4).
- **Reserved words** are `version`, `functions` and `exclude`; inside
  `exclude` the keys are the predicate vocabulary of §4 (`any`, `all`,
  `not`, `tag`, `filename`). Only `exclude` sits where a handler parameter
  could: a handler declaring a parameter named `exclude` is an
  `addon.signature` P1 at load, reported like any other bad signature. The
  list may not grow at the parameter level without a `version` bump.
- YAML is read with `safe_load`. The file is UTF-8.

### 3.2 Placement and scope

- **One optional file per folder**, named `.tfsfunctions.yaml`, anywhere in
  the data tree.
- **Never indexed.** The name is carved out wherever it appears — no `files`
  row, no hash, no `added`/`modified` handler ever sees the control file as
  content. The leading dot is the whole convention.
- **Scope** is the folder holding the file *and everything below it*. There
  is no glob, no path pattern and no reserved "everything" key: root-wide
  rules are a file in the root folder.

### 3.3 Merging

A file's effective configuration is the **union** of every
`.tfsfunctions.yaml` from the root down to its own folder, **parent first**;
within one file, document order. This is v1's `@@` inheritance unchanged —
only the place the declaration lives has moved.

- Two entries for the same handler with **different** parameters both run, in
  that order. This is v1's `@@resize__800/x/@@resize__400/`, which ran twice
  by design.
- Two entries for the same handler with **identical** parameters produce one
  run, because they produce one run key (§7). A child folder repeating its
  parent's entry changes nothing.

## 4. Exclusion

`exclude` belongs to **one entry** and narrows only that entry. Its value is
a **predicate tree** — one shape that every future question about a file
fits into, rather than one keyword per question:

```
exclude   := null | predicate | [predicate, …]     # a list means "any of them"
predicate := {tag: name | [names]}                  # the file carries the tag (any of them)
           | {filename: glob | [globs]}             # its name matches (any of them)
           | {any: [predicate, …]}
           | {all: [predicate, …]}
           | {not: predicate}
```

```yaml
exclude:                                # the common case: a list, read as "any"
  - tag: draft
  - filename: ["*.tmp", "*.bak"]
exclude:                                # the general case
  all:
    - tag: big
    - not: {filename: "*.jpg"}
```

- **One rule for lists everywhere**: a list where a single predicate goes
  is `any` of them; a list where a single value goes (`tag: [a, b]`) is any
  of those values. A predicate mapping has exactly one key.
- **`tag` tests the file's full tag set** — everything inherited from every
  ancestor segment, its own name, and tags applied at run time through
  `ctx.tag` or the API. The same set `tfs query -t` matches.
- **`filename` is a glob against the filename alone** (`fnmatch`), matched
  **case-insensitively** — one root is read from NTFS and ext4 both — at
  every depth the entry covers. Path-relative patterns (`raw/*.jpg`) are not
  supported: a nested folder carries its own file instead.
- **An empty `all` is refused** (it would hold for every file); an empty
  `any`, or an empty list, excludes nothing.
- **The reason `tfs explain` prints is the branch that held**, rendered:
  `tag draft`, `filename *.tmp`, `all(tag big, not(filename *.jpg))` —
  for `any`, the first branch in document order.
- **A new kind of leaf** (a MIME family, a size, an age) is one class and one
  parser branch; `any`/`all`/`not` need no change, and `tfs explain` renders
  it without being told.
- **An exclusion is not a ban.** A deeper folder that declares the same
  handler itself runs it, inside the very subtree an ancestor excluded. That
  is the carve-out case; `not` is for saying what a file is *not*, never for
  undoing an ancestor.

Worked example, against the tree the file in §3.1 sits in:

```
./--tag1/.tfsfunctions.yaml
./--tag1/test1.jpg                 resize ✓   make_copy ✓
./--tag1/test2.jpg                 resize ✗ (filename)   make_copy ✓
./--tag1/--tag2/test1.jpg          resize ✗ (tag2)       make_copy ✓
./--tag1/--tag2/test2.jpg          resize ✗ (both)       make_copy ✓
```

## 5. What fires a handler

| Handler | Runs when |
| --- | --- |
| `added` / `modified` / `removed` | **only** where a `.tfsfunctions.yaml` entry names it |
| `tagged("x")` | globally, for every file carrying `x`, with no parameters — **unless** a folder's file names that handler, which suppresses the default for that subtree and configures it instead |
| `on_start` / `on_stop`, `crit` / `err` / `warn` / `info` | on loading the script. They have no file and no scope, so they need no entry |

The exemption in the last row is not tidiness: requiring an entry for the
problem handlers would mean a misconfigured YAML silently disables the
mechanism that reports misconfigured YAML.

Consequences for the add-on API:

- **`@action.tagged` survives** as an add-on's built-in default for a tag —
  the zero-configuration path, argument-free as in v1.
- **A handler nothing names never runs.** Dropping a script into `script/`
  starts no work anywhere; an entry with no parameters (`thumbnail: {}`) is
  how a parameterless handler is switched on.
- **`addon.duplicate_handler` is deleted.** Two `@action.added()` functions in
  one script are now legal and individually addressable; uniqueness is what
  Python already guarantees — one function name per module. The rule existed
  only because a second handler on the same hook could never be keyed apart,
  and §7 keys them apart.
- **The YAML cannot restrict hooks.** A function marked both `added` and
  `modified` fires on both; splitting it in two is free now.
- **A handler's public name is its `__name__`.** Renaming the function breaks
  every entry naming it (`functions.unbound`, §8) and changes its run key.
  There is no `name=` decorator argument: one name, in one place.

## 6. Entering and leaving scope

| Event | Fires |
| --- | --- |
| a new file appears in scope; a file gains a tag that un-excludes it; a reload adds an entry covering it | `added` |
| the file moves out of the folder, loses the tag by `ctx.untag`, or **gains** a tag the entry excludes | `removed(on_move=True)` |
| the file is really deleted | `removed` |
| an entry is deleted from a `.tfsfunctions.yaml` | nothing |

"In scope" is the thing that changed; how it changed is not the handler's
business, so all three ways out are one event. The last row is the exception
and it is deliberate: a one-line deletion would otherwise start one `removed`
run per file in a 40 000-file subtree at the next reload.

`@action.removed(on_move=True)`'s meaning is unchanged in substance — "the
file left the scope of the function" — only the scope is now the folder
rather than the `@@` directory, which is the same subtree diff
`services/daemon.py` already computes for a move.

## 7. Run identity

```
key = (file_hash, action, handler, hook, args)
```

- **`handler` is new.** Two handlers in one script must key apart; `action`
  stays the script name so "everything `photo.py` ever did" and "everything
  `resize` ever did" are both one `WHERE`.
- **`args` is the entry's parameters**, by name, in their YAML types —
  `{"width": 800}`, not `{"width": "800"}`.
- **Neither the folder nor any tag is in the key.** Identical work happens
  once: the same entry inherited from two folders, or repeated verbatim in a
  child, is one run. Moving an entry between folders re-runs nothing.
- Everything else in v1 §6.1 stands: a run starts iff no row of any status
  has that key; a new hash re-runs; an edited script does not; `failed` and
  `interrupted` keys stay dead until `ctx.retry`.
- **`slug` becomes display text** — `photo.resize(width=800)` — and stops
  being parsed. `ctx.retry` reconstructs a run's arguments from `args_json`,
  where they have always been, instead of re-parsing the marker text out of
  `slug` as `addons/runner.py` does today.

### Schema (migration 3)

```sql
ALTER TABLE actions     ADD COLUMN handler TEXT NOT NULL DEFAULT '';
ALTER TABLE action_runs ADD COLUMN handler TEXT NOT NULL DEFAULT '';

DROP INDEX idx_action_runs_key;
CREATE INDEX idx_action_runs_key
  ON action_runs (file_hash, action_name, handler, hook, args_json);
```

`actions` is registered per `(name, handler, script_hash)`; its `UNIQUE`
constraint is rebuilt to match. Historical rows keep `handler = ''`, which
is not a legal Python identifier, so no v1 run can collide with a v2 key.
`SCHEMA_VERSION` becomes **3** — still a one-line integer literal, because
`tfs upgrade` reads it out of the target tag with a regex
(`DESIGN/v0-2-0.md` §9).

**Every file re-runs once** on the first 0.4.0 start, because `"800"` and
`800` are different keys. This is accepted, not worked around: stringifying
arguments for key purposes would make the key lie about what ran, and
rewriting historical `args_json` would have to guess whether a v1 `"800"` was
meant as an int. `tfs upgrade`'s consent prompt — which already fires when
the schema changes — says so.

## 8. Loading, reload and errors

Configuration is read at **`tfs start`** and at **explicit `tfs reload`**,
never on the watcher's own initiative. `reconcile()` already walks every
directory at both moments, so reading one extra file per directory costs one
`stat` each.

A `.tfsfunctions.yaml` changing under the watcher raises a P2 `functions.drift`
naming the folder and is **not applied**. Editors write files in pieces; a
half-written script fails to import, but a half-written YAML parses cleanly
and applies the wrong arguments successfully. Reload is the commit.

| Failure | Severity | Effect |
| --- | --- | --- |
| `functions.parse` — YAML syntax error | P1 | that file's **previously loaded** version stays in force |
| `functions.version` — `version:` newer than this code | P1 | same |
| `functions.unbound` — no such script, or no such handler in it | P1 | that **entry** is skipped, the rest of the file applies |
| `functions.signature` — unknown parameter, missing required one, wrong type | P1 | same |
| `addon.signature` — a handler declares a reserved parameter name | P1 | existing rule, at add-on load |
| `name.parse` — a `@@` marker in a name | P2 | existing rule, marker skipped |

One folder's broken file never takes the root down, and it never silently
reverts to "no rules" either — keeping the last good version is what a
running daemon does with a broken script today.

An entry that is valid but matches no file is **silent**. There is no
"unused rule" warning: a folder that is empty today is not a mistake.

## 9. CLI

| Command | Behaviour |
| --- | --- |
| `tfs list` | per **handler**: script, handler, hooks, parameter schema — plus the load problems of `script/` and of every `.tfsfunctions.yaml` |
| `tfs explain <path>` | the effective handlers for one file: each with the folder that contributed it, and each *suppressed* one with the rule that excluded it |
| `tfs migrate` | §10 |
| `tfs init` | additionally writes a commented `.tfsfunctions.yaml` skeleton in the root |

`explain` is not a convenience. A file's configuration is now a merge across
every ancestor folder, minus per-entry exclusions, plus global `tagged`
defaults that a nearer folder may have suppressed — and unlike a `@@`
directory name, none of that is visible by looking at the file. The loader
computes exactly this merge to decide what to run; `explain` prints it.

Both follow the existing client-first rule (v1 §8): the daemon answers if it
is up, otherwise the CLI loads `script/` and walks the tree itself. `/actions`
reports per handler to match `tfs list`.

## 10. Migrating a v1 root

`tfs migrate` converts `@@` directories into configuration. The conversion is
exact: the directory gives the script and the positional arguments, and the
loaded handler's signature gives the parameter names those positions map to.

- **Dry run by default.** It prints every file it would write and every case
  it cannot convert — no such script, an arity that does not fit the
  signature, a `@@` marker on a *filename* rather than a directory. `--apply`
  writes them.
- **Renaming is a separate step.** `tfs migrate --rename`, with its own dry
  run, strips the `@@…` markers from folder names and keeps their `--tags`.
  It is not a side effect of writing configuration: renaming a directory in a
  watched root moves every file underneath and the daemon sees the whole
  subtree leave and re-appear. Migrate, verify the runs, then clean up the
  names.
- Until the rename, the old directories emit one P2 `name.parse` per file.
  That is the reminder.

## 11. Delta from 0.3.x

- `core/interface/tag.py`: `ActionCall` and `ParsedPath.actions` deleted;
  `MARKER_PREFIXES` keeps `@@` only so it can be rejected; `ARG_SEPARATOR`
  goes.
- `services/tagging.py`: the `actions` target field and its factory go;
  `split_extension` loses `@@`/`__` from its marker test.
- **New `functions/`** (loader + model): reads and validates
  `.tfsfunctions.yaml`, merges the ancestor chain for a path, applies
  `exclude`, and answers "what applies to this file" for both the runner and
  `tfs explain`.
- `addons/loader.py`: handlers addressed by name; `addon.duplicate_handler`
  deleted; `Addon.describe()` reports per handler; reserved parameter names
  rejected.
- `addons/binding.py`: binds a `dict` by name instead of a tuple by position;
  `raw_by_name` goes; `TagDir`/`Remote` resolution unchanged.
- `addons/runner.py`: `on_file` iterates the merged configuration instead of
  `parsed.actions`; `retry` reads `args_json`; `RunKey` gains `handler`.
- `services/daemon.py`: `_moved`/`_removed` diff *configuration* scope rather
  than parsed actions; reload re-reads the tree.
- `database/migrations.py`: migration 3, `SCHEMA_VERSION = 3`.
- `cli.py`: `explain`, `migrate`, `init` scaffolding, per-handler `list`.
- `pyproject.toml`: PyYAML. `config.toml` stays TOML and `updater.py` stays
  standard-library-only — it never reads this file.
- `CLAUDE.md`: the versioning rule is reworded in the same commit — **A** = an
  existing root stops loading or loses data; **B** = new behaviour, including
  grammar changes a root survives with a warning. This release is a **B**.
  `README.md` follows.

## 12. What this replaces in v1

- **§3 Name grammar** — the `@@` marker, `func`/`arg` rules, the `__`
  separator, and the extension rule's dependence on them.
- **§4.1** — `@@foo` without `script/foo.py`; §4.2's one-handler-per-hook rule.
- **§4.2 / §4.4** — positional arguments bound by position; parameters are
  named and typed, but `TagDir` and `Remote` are unchanged.
- **§6.1** — the run key gains `handler`; "`@@` directory renamed → every file
  inside re-runs" becomes "the entry's parameters changed → every file in
  scope re-runs".
- **§8** — the command list grows `explain` and `migrate`.

Everything else — reconciliation, hashing, moves, provenance, problems and
their replay, the control channel, the lock, `ctx`, chain depth, the severity
table — stands as written.

## 13. Out of scope

- **Path patterns as scope.** `"2024/**/*.jpg":` as a selector reintroduces
  literal paths, which v1 §4.4 removed on purpose. A nested folder gets its
  own file.
- **A `disable:` list** for switching off a global `tagged` default without
  configuring it. Naming the handler in a folder's file already suppresses it;
  if that turns out too blunt, `disable:` can be added without breaking a
  `version: 1` file.
- **Per-entry hook selection.** §5.
- **Rewriting historical `args_json`.** §7.

## 14. Implementation notes

Where the code, as shipped in 0.4.0, deliberately differs from or narrows the
text above:

1. **`actions` rows stay per `(name, script_hash)`** — one row per loaded
   script version, as before. The handler dimension lives in
   `signature_json` (`{handler: schema}`) and `hooks_json`
   (`{handler: [hooks]}`); `handler` was added to `action_runs` only, and
   the key index rebuilt. §7's "registered per `(name, handler,
   script_hash)`" would have meant rebuilding a table that `action_runs`
   references inside a transaction that already has foreign keys on;
   nothing observable depends on the difference.
2. **A TAGGED run's key carries the tag**: a global default keys
   `{"tag": T}` as in v1, a configured `tagged` handler keys
   `{"tag": T, **entry.args}`. Hence `tag` is a reserved parameter name on
   any function marked `tagged` (an `addon.signature` at load), alongside
   `exclude`. A configured `tagged` handler also fires when a file *enters*
   scope already carrying its tag (`on_file(ADDED)` fires the TAGGED marks
   whose tag the file has); the key makes the double offer one run.
3. **Errors inside one handler block** (a non-mapping block, a malformed
   `exclude`, a parameter name that is not a string) are
   `functions.signature` and skip that entry; only the document skeleton
   (YAML syntax, not a mapping, an unknown top-level key, `functions` or a
   script's value not a mapping) is `functions.parse` and refuses the file.
   A `null` handler block is `{}`; a missing `version` is `functions.version`.
4. **A `tagged` default is suppressed** for a file when a *valid* entry in
   its folder chain names `(script, handler)`, excluded or not. An entry
   skipped as unbound or ill-typed does not name it — its P1 is the signal.
5. **`start` and `reload` reconcile with every entry in scope offered again**
   (`on_transition(..., rescope=True)`); the run key makes finished work a
   `find_run` hit. That is how a reload's new entry reaches the files it
   covers, and how the first 0.4.0 start re-runs everything once (§7). A
   file whose content changed while the daemon was down gets `modified`, not
   a second `added`.
6. **`ctx.emit` / `ctx.write` over a file that already has a row** fires
   `modified` (new hash), not `added`; the watcher's later event for the
   same write finds the key and is a no-op.
7. **Handler identity** is `__name__`, falling back to the module attribute
   for a nameless callable (a `functools.partial`); two distinct functions
   sharing a name in one script → the second is `addon.signature`.
8. **`functions.drift`** is raised once per folder until the next `reload`
   (by the watcher, and by a reconcile that finds the file on disk differs
   from what was loaded — a file that appeared while the daemon ran
   included). A file deleted under the watcher keeps its last-good
   configuration until reload.
9. **`ctx.retry`** rebuilds the arguments from `args_json` and, before
   starting, checks them against the handler's current signature: a
   parameter that no longer fits is `retry.key_changed`, as a changed key
   was in v1. A row written before schema 3 (`handler = ''`) is refused the
   same way.
10. **`tfs init`** writes the skeleton itself, after `Root.init` returns:
    the file is data, not layout, and `Root.init`'s rollback stays as it is.
11. **`tfs migrate --rename`** renames every folder whose name carries a
    `@@` marker — including one whose configuration was written by hand
    (the file travels with the folder) — and only skips a target that
    already exists. A name that would come out empty (`@@resize__800`)
    becomes the call spelled with hyphens (`resize-800`). A file migrate
    wrote is recognised by its header, so a second `--apply` neither
    rewrites nor reports it.
12. **`binding.by_position`** survives as the one place the v1 positional
    rule is spelled, for `migrate`; `bind` is by name. `binding.check`
    (validation without resolving `TagDir`/`Remote`) is what the store
    validates entries with and what `tfs migrate` types values with.
