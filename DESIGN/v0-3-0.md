# TagFileSystem — v0.3.0 Design: daemon lifecycle hooks

**Status:** approved 2026-09-02, implemented 2026-09-02 (shipped in 0.3.0).
This document is the target behaviour for the 0.3.0 release; `CLAUDE.md`
describes the code as it currently is. Where they differ, this document wins
for anything being built. It extends [`v0-1-0.md`](v0-1-0.md) and
[`v0-2-0.md`](v0-2-0.md) and does not replace them: everything those documents
specify still holds.

## 1. Purpose

Give an add-on a place to run when the daemon comes up and when it goes down.

Every hook in v1 is about a *file*: something appeared, changed, left, or
acquired a tag. An add-on that needs a connection, a session, a cache, a
scheduler thread or a "the watcher is back" notification has nowhere to put
it — the first file event pays for the setup, nothing tears it down, and an
add-on that has no file work at all (a heartbeat, a nightly sweep) cannot be
written as an add-on at all. Two hooks fix that.

## 2. The hooks

```python
from tag_file_system import action

@action.on_start()
def up(ctx): ...

@action.on_stop()
def down(ctx): ...
```

- **Shape.** `(ctx)` and nothing else, the way a problem handler is
  `(problem, ctx)`. There is no file, so there is no `path` and no `metadata`;
  a parameter after `ctx` that has no default is a load-time
  `addon.signature` P1, exactly as for a problem handler. There are no
  arguments to bind: a lifecycle hook is never spelled in a name, so nothing
  can pass it one.
- **One per add-on per hook**, like every other hook: a second `on_start` in
  one script is an `addon.duplicate_handler` P1 and is skipped.
- **A script may carry only lifecycle handlers.** That is not an empty add-on
  and raises no `addon.empty` warning.
- **`ctx` is the full `ActionContext`** — `write`/`copy`/`emit` and their
  provenance, `record`/`log`, `spawn`/`done`, `problem`, `query`, `tag`,
  `resolve` all work. `ctx.file` and `ctx.path` are `None`: this run is about
  the daemon, not about a file.

## 3. When they fire

| Moment | What happens |
| --- | --- |
| `tfs start`, after the add-ons load, before the first file is looked at | `on_start` for every loaded add-on |
| a script appears (or a broken one starts importing) while the daemon runs, `tfs reload` included | `on_start` for that add-on only |
| `tfs stop`, a signal, a failed `startup()` — before in-flight runs are waited for | `on_stop` for every loaded add-on |

`on_start` runs **after** the loader and **before** `replay_undelivered()` and
the opening `reconcile()`: a notifier set up in `on_start` therefore hears the
problems a crashed session left behind, and a handler that prepares a
directory or a connection is ready before the first file run needs it.

`on_stop` runs **before** the runner waits for in-flight runs, so a handler
that signals a service thread to leave lets `stop_timeout_seconds` apply to a
thread that is already on its way out — rather than to one that has not been
told anything. A run that an `on_start` left open (`ctx.spawn` without
`ctx.done`) is finished by the thread itself; one that is still running when
the timeout expires is `interrupted` (P0) like any other run.

Ordering within one moment is by add-on name, so a session does not depend on
the order the filesystem lists `script/`.

A script *deleted* while the daemon runs gets no `on_stop`: its module is
dropped, and there is nothing left to call. An add-on that must survive that
should not be deleted while it runs.

## 4. Run identity

A lifecycle handler produces an ordinary run row — recorded, traced, and
attributable like every other run (v1 §6.2). It is keyed as

```
key = ("", action, hook, {"session": <this daemon session>})
```

- **No file, so no `file_hash`**: the empty string says so, `file_id` is NULL,
  and the run's `slug` is the hook name.
- **The session is what makes it unique.** One `on_start` per add-on per
  daemon session: the key is what enforces it, which is why the "fire it
  again after a load" rule of §3 costs one indexed lookup and cannot
  double-run an add-on that already had its turn. A restart is a new session
  and runs again.
- **An edited script does not re-fire.** The key does not contain the script
  hash, so a hot reload during a session is not a new start — consistent with
  v1 §6.1 ("script edited → no automatic re-run").
- **`source` is `lifecycle`**, a new `RunSource`, so `on_start` runs are not
  confused with the reconcile pass that follows them.
- **Not retryable.** `ctx.retry` on a lifecycle run is a `retry.lifecycle` P2
  and does nothing: the session it belonged to is the thing that happened, and
  it cannot be made to happen twice. A failed `on_start` is a P1 `run.failed`
  like any other failure, and the add-on's file handlers still run — the
  daemon does not refuse to start because an add-on's setup failed.

## 5. A run that lasts the whole session

`on_start` plus `ctx.spawn` is how a service add-on is written, so a lifecycle
run may legitimately stay `running` for days. Two v1 rules assume runs are
short and have to be told about it:

- **`observed` attribution (v1 §6.3) skips lifecycle runs.** "A run was in
  flight when this file changed" is evidence only if the run's lifetime is
  narrow; a session-long run would make every change of the session
  `observed`, and `ambiguous` as soon as a second run overlapped it. The
  signal is worth more than the edge, so a lifecycle run is never a candidate.
  Files it writes through `ctx` still record `emitted` provenance, which is
  the authoritative half anyway.
- **`run_warn_after_seconds` skips lifecycle runs.** A service crossing the
  threshold is not late, and a P2 per session — delivered to whatever notifier
  the user wrote — is a false alarm they cannot silence. A lifecycle run that
  never ends is still `interrupted` (P0) at shutdown, which is the honest
  report.

## 6. Schema

None. `action_runs.hook` and `.source` are free text, `file_id` is nullable
and `file_hash` is `NOT NULL` but not constrained — `SCHEMA_VERSION` stays
**2** and a 0.2.x database needs no migration. A 0.2.x binary reading a 0.3.0
database sees run rows whose hook it does not know; it never dispatches on
them, so this is backwards compatible in both directions.

## 7. Delta from 0.2.x

- `action.py`: `on_start()` / `on_stop()`, `HandlerSpec.kind == "lifecycle"`.
- `core/interface/action.py`: `Hook.ON_START` / `Hook.ON_STOP` and
  `Hook.is_lifecycle`; `RunSource.LIFECYCLE`.
- `addons/loader.py`: `LifecycleHandler`, `Addon.lifecycle_handlers`,
  `AddonLoader.lifecycle_handlers(hook)`, and `Addon.describe()` — the one
  place that says what `tfs list` and `/actions` report about an add-on.
- `addons/runner.py`: `on_lifecycle(hook)`, the per-session id, and `_invoke`
  — the run body that a file run and a lifecycle run share.
- `services/daemon.py`: `on_start` in `startup()` and after every later load,
  `on_stop` in `shutdown()`; `_observe` ignores lifecycle runs, as does
  `check_overdue` (§5).

## 8. Out of scope

- **Periodic hooks.** `@action.every("5m")` is the obvious neighbour and is
  deliberately not here: it needs a scheduler, a catch-up policy for a daemon
  that was down, and a run key that is a time window rather than a session.
  `on_start` plus `ctx.spawn` covers the cases that cannot wait, and does it
  with the machinery that already exists.
- **Per-add-on shutdown.** An `on_stop` when a single script is deleted or
  reloaded (§3) would need the loader to keep the old module alive long enough
  to call it, and to decide what a half-replaced add-on is. Not worth it until
  something asks for it.
